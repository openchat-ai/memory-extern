## #26 合成 fact set 的 key 退化（2026-10-21，实验设计坑）

**现象**：自造 100 条事实（10 个模板只换数字）测不同 readout，
所有方法都退化到"输出同一常数"（`' yes yes yes...'`），且层 23-27 处
**两两余弦 mean +0.953、检索权重 max 占比 0.0115 ≈ 均匀基线 0.0100**。

**证据**：`docs/HEB_EXPERIMENT.md` §10.9.1/§10.9.4；
真实多样 key 对照（同 32 条）layer 22 处余弦 mean +0.319、检索占比 0.2556 → 有区分力。

**可能价值**：解释了大量"所有方法都失败"的假阴性结果。
**待查方式**：任何"写入 N 条事实"的 benchmark，**先测 key 两两余弦 + 检索权重 max 占比**，
若 max 占比 ≈ 1/N（均匀）则该 fact set 无区分力，结论作废（§11.8）。

## #27 单层交付版无干净窗口（2026-10-21）

**现象**：单层 27 在 fp32 下命中需 c≥20，而 c=12 起 holdout 就污染 → **窗口为空**；
多写几层（18-22, 5 层）c=5~20 反而全干净。

**证据**：§10.9.2 细扫表 + §10.9.3 Q4T 窗口 [20,32]（层 18-22, c=24 → holdout 0/6）。

**可能价值**：交付版的"少层=快"直觉在此被推翻——**层数少反而需要更大 c**，
总振幅才是主因。已据此产出 `rStar-Coder-hebbit-18-22.gguf`（holdout 0/6）。
**已解决（2026-10-21 §10.9.7/10.9.8）**：**单层 18, c=60** 即 0/6 污染且重打包仅 2.0s
（层 24+ 无干净窗口；层 18-22 是"干净层"）。
**新交付物** `models/qxt/rStar-Coder-hebbit-1L18.gguf`（单层 18 c=60）。
**教训**：层数不是主因，**层的 key 区分力才是** —— 旧单层版选层 27 恰好选中最差的层。


## #28 同模板事实的 φ 区分力在中层最好，但仍不可用（2026-10-22）
