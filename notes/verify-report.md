# MAC 数与数据口径甄别报告

> 结论：上游两次修正（115→34、34→17）都基于错误假设。**34 MAC 是对的，17 MAC 是错的。**

## 1. 根本错误：GEMV 的 bytes/MAC 是 2B，不是 4B

LLM decode = GEMV（矩阵 × 向量）：

```
y[N] = W[N,K] · x[K]
```

- 权重矩阵 W：全量流式读取，是 DRAM 流量主体
- activation 向量 x：只有 K 个元素，一次性读入，被 N 行复用
- **bytes/MAC = 2B**（只算权重），不是 4B

铁证：7B bf16 = 14GB 权重，每 token 做 7×10⁹ 次 MAC → 14GB ÷ 7B = **2B/MAC**

## 2. 两版对比

| 版本 | 假设 | MAC | 正确 2B 口径利用率 |
|------|------|-----|-------------------|
| 778e733（34） | 4B 算出理论 17，手工选 34 | **34** | 34×2B×1.0GHz = 68 GB/s = **100%** ✅ |
| 5e33e52（17） | 4B 交叉验证"34 超订 239%" | 17 | 17×2B×1.0GHz = 34 GB/s = **50%** ❌ 浪费一半 |

若跑 1.2 GHz：34×2B×1.2 = 81.6 GB/s = 120%（超订），**28 MAC×2B×1.2 = 67.2 GB/s = 98%** 更佳。

## 3. 其他硬伤（上游未修）

- **SRAM 晶体管低估 2.5×**：上游按 20,000 T/KB（=2.5 T/bit）。6T SRAM 下限 = 6 T/bit。2MB = **100.7M T**（上游算 41M）
- **14nm 密度矛盾**：process-comparison.md 说 30M T/mm²，estimate/verify 用 55M T/mm²（55M 是 10nm 水平）
- **MPW 成本错误**：¥200万 ÷ 整片晶圆 30309 颗 = ¥66/颗。MPW 是拼片，只拿到几十~几百颗，真实 **~¥2万/颗**（量产另算）
- **verify_calculation.py 造假**：口径2 自己算出 34 MAC = 239% 超订，总结表却硬写"✅ 一致 476 MAC"；基础参数 34 MAC/4MB/2.7mm² 与同提交 est(17/2MB/2.0mm²) 直接冲突

## 4. 权威口径（本报告采用）

```
单芯片带宽:  68.3 GB/s (LPDDR5X 4ch × 2B × 8533 MT/s)
GEMV bytes/MAC: 2B
MAC 数:       34 @1.0GHz (100%)，或 28 @1.2GHz (98%)
晶体管:       MAC 0.14M + SRAM 100.7M + PHY 20M + SerDes 16M + PCIe 15M + 控制 12M + 其他 5M ≈ 169M
面积:         @30M/mm² = 5.6mm²；@55M/mm² = 3.1mm²（待上游确认密度）
MPW 成本:     ~¥2万/颗（拼片口径）；量产需另行询价
```

## 5. 建议

- 架构方向（单芯片带宽受限、多芯片扩展）成立，保留
- MAC 数应回到 **34**（2B/MAC 口径），或按 1.2GHz 取 **28**
- 密度、SRAM 估算、MPW 成本需按 6T / 30M / 拼片口径重算
- 请上游依据本报告做二次评估
