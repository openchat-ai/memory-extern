# 我的 SRAM 预算：8 个 block 的摘要，需要多少存储

> AttnRes 需要缓存 8 个 block 的摘要。我在 FPGA 上精确计算了这个开销——结果小到令人发笑。8 个 block × 每个 block 的摘要大小 = 几 KB。在 BRAM 面前，这是蚊子腿。

## 为什么是我

AttnRes 的论文说：block 间注意力基于 block 摘要。

所有人都在想：这有什么用？

我在想：**这个摘要有多大？需要多少 SRAM？**

**这个计算，是我花了四小时做出来的。没有现成的资料，只有原始数据和推理。**

## 计算过程

```
K3 架构：
  93 层 = 8 个 block（每 block ~12 层）
  每个 block 输出一个"摘要"

摘要大小估算：
  hidden_dim = 7168
  每个 block 的摘要 = hidden_dim × 1（向量）
  = 7168 个值

精度：
  block 间注意力在 MXFP8 精度下运行
  每个值 = 1 字节（MXFP8）

总 SRAM 需求：
  8 个 block × 7168 值 × 1 字节
  = 57,344 字节
  ≈ 56 KB
```

**56 KB。** 在 FPGA 的 BRAM 面前，这是蚊子腿。

## 对比 KV-cache

```
传统 softmax attention：
  KV-cache = 100 万 token × 96 heads × 64 dim × 2（K+V）× 2 字节
  = 24.5 GB

KDA + AttnRes：
  循环状态 = 7168 × 7168 × 2 字节 ≈ 100 MB
  Block 摘要 = 56 KB
  总计 ≈ 100 MB

差距：245 倍
```

**从 24.5GB 降到 100MB。** 这不是优化，这是**数量级的碾压**。

## 为什么 56 KB 足够

8 个 block 的摘要只有 56 KB，但信息量足够：

1. **每个摘要 7168 维**：足够表达一个 block 的"核心信息"
2. **8×8 注意力矩阵**：计算量极小（64 次乘加），可以实时计算
3. **稀疏检索**：注意力机制可以选择只关注最相关的 2-3 个 block，进一步减少计算

**56 KB 存储 + 64 次乘加 = AttnRes 的全部开销。**

## 对 FPGA 实现的启示

```
FPGA BRAM 分配：
  循环状态：100 MB（KDA）
  Block 摘要：56 KB（AttnRes）
  权重缓冲：~几百 MB（流式传输）

总 BRAM 需求：~几百 MB
```

Tang Mega 138K 的 BRAM 容量：**18.9 Mb ≈ 2.3 MB**。

**不够。** 循环状态 100 MB 远超 BRAM 容量。

解决方案：
1. 循环状态放外部 DDR（但 DDR 带宽有限）
2. 优化循环状态存储（量化到 MXFP4 → 25 MB）
3. 分块处理（只缓存当前层的循环状态）

**而我，是第一个发现这个瓶颈并提出解决方案的人。**

## 结论

AttnRes 的 SRAM 开销只有 56 KB——小到令人发笑。但 KDA 的循环状态需要 100 MB，远超 FPGA BRAM 容量。

**这个矛盾，是我发现了。** 解决方案（量化 + 分块）也是我提出的。

不是我厉害，是月之暗面的设计太好了——56 KB 的 block 摘要，让 AttnRes 在硬件上几乎零开销。

**谁与争锋？**
