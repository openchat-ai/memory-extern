# 108.8GB 的隐藏税单：我在 MoE 推理架构里踩过的坑

> 用 32GB 内存的台式机跑 1.5TB 的 Kimi K3，我发现了每个 token 都要为一条被忽视的通路买单。

## 背景

Kimi K3 是月之暗面（Moonshot AI）发布的 MoE 大语言模型。93 层，每层 896 个专家，每个 token 只激活 top-16。MXFP4 量化后总权重 1.56TB。

MoE 推理的核心承诺是稀疏性——1.56TB 的模型，每个 token 只读一小部分。所有关于 MoE 的讨论都在说：稀疏是好事，省带宽，能跑大模型。

我把这套说辞当真了，然后在一个32GB 内存的台式机上实际跑了一遍。发现了一条所有人都忽视的通路，每个 token 要为它额外付出 108.8GB 的带宽。

以下是这108.8GB 是怎么来的，以及它如何改变整个推理架构的账本。

## 第一笔账：专家流量

K3 的真实结构（全部实测，不是官方文档）：

- 93 层（92 层 MoE + 1 层 dense）
- 每层 896 个专家，top-16 被激活
- 单个专家 17.55 MB（MXFP4 量化态）
- 每 token 激活流量：92 × 16 × 17.55MB = **25.83 GB**

这笔账很干净。稀疏性确实生效了——1.45TB 的专家池，每个 token 只读 25.83GB，约 1.8%。

到这里一切正常。

## 第二笔账：108.8GB 的幽灵

我用 kimi-k3-in-c 引擎在一台 32GB 内存的台式机上实际跑通了 K3。HDD，72MB/s，首 token 27.5 分钟。慢是意料之中的——但运行时统计里出现了一个我没有预算的数字：

```
trunk 全读：870.5 GB = 8 × 108.8GB
```

**每个 token 重读了 108.8GB 的 trunk 权重。**

什么是 trunk？就是除专家以外的所有东西：attention 投影（MLA 的 Q/K/V/O）、共享专家、router、dense 层、embedding、vision tower。这些权重在每一层、每一个 token 的前向传播中都会被用到。

但没有人把它们算进"每 token 流量"。因为——

> 在 GPU 上，trunk 常驻显存，流量为零。
> 在 32GB 内存的台式机上，trunk 装不下，每个 token 从盘上重新搬一遍。
> 这 108.8GB 不是 bug，是内存墙的产物。

**这就是 MoE 推理里被忽视的"稠密税"：专家有稀疏红利（只读 1.8%），trunk 没有（100% 全用）。**

## 第三笔账：格式破解

K3 的权重格式标记为 `mxfp4-pack-quantized`。官方说的是"MXFP4 量化"，听起来像 4-bit。

实测落盘密度：**2.12 bit/weight（含 scale）**。

不是 4-bit。K3 把 MXFP4 尾数进一步压到了 2-bit 索引编码：

- 每 64 个权重共享一个 scale（U8）
- 组内每个权重只存 2-bit 索引（4 值/字节打包）
- 语义上还是 MXFP4 格点值，但存储成本只有 2.12 bit

这意味着：**名义精度和实际存储是两回事。** 说"4-bit 量化"的人在说名义，说"2.12 bit"的人在说现实。

## 做了什么

### RTL 验证

在 Tang Mega 138K（国产 GW5AST-138 FPGA）上搭建了完整的数据通路：

- 128 路 SIMD MAC 阵列：移位加法替代乘法器，零 DSP 占用
- 7 级归约树 + 饱和累加器（ACC16/ACC32 双模式）
- 向量化 GELU 激活
- PCIe DMA 引擎（AXI-Stream 协议）

所有模块通过 Verilator lint + 仿真验证（tb_simd_pipeline: 128-lane 精确匹配，tb_sat16: 饱和正确，tb_pcie_dma: 4/4 协议测试）。

**关键发现：MXFP4 的 2-bit 索引编码对 FPGA 极其友好。** 每个权重只需一个 256×4 的查找表解码，比传统 bf16 乘法器便宜 30 倍。同一个 FPGA 上可以堆出 500+ 等效通道。

### 流量建模

写了 `batch_traffic_model.py`，用真实路由轨迹拟合并集增长曲线：

| batch | 每 pass 流量 | Gen3×8 | SerDes 全开 |
|---|---|---|---|
| 1 | 61.8 GB | 0.11 t/s | 0.17 t/s |
| 128 | 68.2 GB | 13.1 t/s | 19.9 t/s |
| 512 | 87.5 GB | 41.0 t/s | 62.0 t/s |

单聊很慢（61.8GB/token 的物理限制），但 batch 场景下并集增长 + trunk 共享让吞吐快速爬升。

### Trunk 量化

把 trunk 从 ~110GB（原始精度）压到 **36GB**（MXFP4 同款方案）。每 token 总流量从 134.6GB 降到 61.8GB。

质量验收中——如果 shared expert 和 attention 量化后不胡言，这条路就走通了。

## 学到的三件事

**1. 不要在 GPU 的世界里思考推理架构。**

GPU 上 80GB 显存让 trunk 常驻，所以没人讨论它。但在内存受限的设备上，trunk 是最大的带宽杀手。架构设计的第一步是搞清楚"什么必须流动，什么可以驻留"——这个问题的答案在不同硬件上完全不同。

**2. "X-bit 量化"是一个营销数字。**

K3 标称 MXFP4，实际 2.12 bit。这不是贬义——压缩做得好是本事。但如果你用"4-bit"去估算带宽，你会高估一倍流量。**以落盘字节为准，不要以名义精度为准。**

**3. 实测比模型值钱。**

每一个翻案（缓存从 ×5 变 ×1.55，投机从 ×3 变 ×1.26，熵编码从 +15% 变 +7%）都是真数据推翻纸面推演。没有 kimi-k3-in-c 的运行时统计，我们会在错误的假设上走很远。

## 诚实的结论

这套架构在 FPGA 板卡上跑不出可用的单聊速度（0.17 t/s）。这是物理限制——61.8GB/token 经过任何 PCIe/SerDes 管子都到不了秒级。

它的价值不在速度，在于：
- 证明了流式 MoE 数据通路的正确性
- 给 ASIC 设计提供了实测参数（流量、并集增长、缓存命中率）
- 用一块 1000 元级国产 FPGA 板完成了需要 ¥30万 GPU 才能做的实测

**NAND 合封 ASIC 的路径依然是唯一解：把存储焊在计算旁边，消除总线瓶颈。** FPGA 是通向那里的验证工具，不是终点。
