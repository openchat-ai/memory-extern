# Qwen → K3 结构借鉴（实测定案)

> 问题：把 Qwen 的优点用到 kimi-k3 上。逐一核对"哪些是 Qwen 有、k3 缺/弱的"，
> 用双方 trace 数据实证，别凭印象。工具：k3=`struct_check.py` / `shared_expert_sim.py` 复盘。

## 一、先纠正——三条"以为能借"其实是反的
| 我早先提的"Qwen→k3" | 实测定性 |
|---|---|
| shared_experts | **反**：shared_experts 是 k3 v2 层自己有的，Qwen 反而没有 |
| 物理 trunk 打包 | **反**：trunk.bin(108.8GB)+索引是 k3 自己有的，Qwen 没有 |
| prefill 分阶段(16→256→64) | **成立**：k3 缺，见下 |

## 二、真正的借鉴点（实测数据）

### 借鉴 1 · "整层工作集一次装载 + 常驻"，不做 10× 重复装载 ★核心
k3 trace（`expert_trace.bin`）实测量化：
- **100,096 次装载请求，只有 10,010 个唯一专家 → 重复装载 10.00×**
- 每层 8 个 run 的专家集合 **100% 重合**（同层首 run 平均 62 专家，其余 7 遍照单重发）
- 也就是：k3 把同一层同一批专家**连发 10 遍**，中间还夹着别的层 → 把局部性打散成 36%

Qwen 对照（`trace-4`）：prefill 用 **256（整层全量一次）** → decode 每 token 只路由 **8 个**，
**无任何"同层重复装载同一批专家"结构**。这就是 Qwen 能 90-100% 的装载形态。

**移植动作**：k3 应把"每层 8 遍 × 同专家集"合并为**一次整层装载 + 常驻**（等价 layer-first 重排
的实机编码，README §5.11 已证 90%）；这同时把装载量从 100,096 降到 ~10,010，**装载字节直接省 10×**。

### 借鉴 2 · 常驻后的小活跃子集 + LRU
合并装载后，decode 用一个小的活跃专家子集 + LRU 捕捉幂律热尾（Qwen 用 8 专家/token +
~120-243 槽/层即 90-100%）。k3 装机形态：整层工作集 resident + 小 LRU 处理增量。

## 二之补 · 数字纠偏（研究者自我审计：÷10 是虚的，÷6.38 才实）

早先我写"装载量 ÷10"，严谨复核后**缩水**：

| 指标 | 原始顺序 LRU@150槽 | 层优先/预测式(最优) | 比值 |
|---|---|---|---|
| 装载请求数 | 100,096 | 100,096（不因重排改变） | 1.0× |
| **实际从磁盘读的专家数(miss)** | 63,824 | 10,010 | **÷6.38** |
| **磁盘读取字节** | 1,119.94 GB | 175.65 GB | **÷6.38** |

- "÷10" 是我把 **请求数比(100096/10010)** 误当成了**磁盘字节比**。
- 真正的"装载字节"是 **miss 数决定的**，最优 → 175.65GB = **÷6.38**（非 ÷10）。
- ÷6.38 的来源 = **命中率 90% 让 90% 的访问被缓存吸收**，不是"删除/合并请求"。

## 三、为什么这条借鉴成立（诚实边界）
- 这是 **cross-model 独立佐证**：Qwen 的 prefill/decode 分离是它自己的架构事实，
  恰好把 README 已得出的 layer-first 结论用**独立模型**再证一遍 → 比单模型自查硬。
- **不成立的部分**：Qwen 不提供"训练出的共享专家"（k3 的 shared_experts 优势仍在 k3 这边），
  也不提供物理 trunk 打包格式。这些不用从 Qwen 学。
- 落到 k3 真机：合并装载 = 装载量 ÷6.38，天然解掉"194GB/token 装载"的 memory-bound 主因
  （README/HANDOFF 的瓶颈判断），优先级最高。

## 四、真正的风险（你担心"研究到最后不可行"——就卡在这）
**÷6.38 只在"命中率 90%"成立。而 90% 有两种取法，一条在线一条离线：**

| 路径 | 命中 | 磁盘字节 | 在线？ | README 判定 |
|---|---|---|---|---|
| layer-first + LRU（整层合并装载） | 90.00% | 175.6 GB (÷6.38) | ❌ **离线** | 在线批≤5000 只 36% |
| predictive + LRU（历史热度预取） | 88.46% | 202.7 GB (÷5.5) | ✅ **在线** | **可信度=中，缺真机验证** |

**风险定点**（README 原文 §5.11 + HANDOFF 已标注）：
1. layer-first 的 ÷6.38 是离线理想：现实逐 token 推理**拿不到全量请求**去重排，
   在线批内聚拢（≤5k token）只回落到 36% → **离线 ÷6.38 在线不可达，除非改用预测式**。
2. 唯一在线可达的预测式 = 88.46%，但它只得到 **÷6.3 的 98%**——也就是说：
   **÷6.38 本身真实，但它的在线对价取决于预测式预取能否在真机兑现**，而这正是
   仓库标注"缺真机验证"的开放项（README 待办：①②多 trace 验证层热度）。
3. 若预测式在真机翻车 → 在线只剩 36%，÷6.38 落空 —— 这就是"研究到最后发现不可行"
   的唯一真实坍缩点，且已精确定位：**在预测式预取的真机验证上，不在"装载合并"本身。**

复现：
```bash
python3 sim_cache.py data/expert_trace.bin --slots 150 --policy lru,predictive
# → trace 顺序: LRU 36.24 / PREDICT 88.46 (MISS 63824→~11500, GB 1119.94→~200)
# → layer-first: LRU 90.00 (MISS 10010, GB 175.65)
```
