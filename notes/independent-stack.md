## 一、项目定位

> 一句话：**用标准逻辑硅把万亿 MoE 模型变成一台便宜的消费级设备。**

### 目标模型：Kimi K3 官方架构

K3 是月之暗面（Moonshot AI）于 2026 年 7 月发布的旗舰开源模型，2.8T 总参数，104B 激活参数。核心技术：

- **KDA（Kimi Delta Attention）**：混合线性注意力，93 层中 69 层用 KDA、24 层用 Gated MLA（3:1 比例）。KDA 维持固定大小循环状态，支持 1M token 上下文
- **AttnRes（Attention Residuals）**：93 层分 8 个 block，block 间用注意力机制选择性检索前序层表征
- **Stable LatentMoE**：896 专家，top-16 激活，Quantile Balancing 路由均衡，SiTU-GLU 激活函数
- **QAT 量化**：从 SFT 阶段起量化感知训练，MXFP4 权重 + MXFP8 激活，落盘密度 2.12 bit/weight

**本项目关注的推理带宽问题**：trunk（KDA 门控投影 + Gated MLA Q/K/V/O + 共享专家 + router + dense + embed + vision）每 token 每层必经，无法稀疏化。实测 108.8GB/token（未量化 trunk），MXFP4 量化后降至 36GB。**定案保 fp16（2026-08-29，见 k3-verdict §八修订）**。详见 `k3-verdict.md`。

三条路线并行：

| 路线 | 核心创新 | 目标市场 |
|---|---|---|
| A. 片上固化推理盒 | 权重烧入片上 ROM，上电即推理 | 嵌入式/边缘/单模型 |
| B. NVMe 流式加速卡 | 预测预取 + 便宜硬盘当容量 | 有主机的工作站 |
| C. NAS+AI 双模一体机 | 不跑 AI 就是高端 NAS | 个人/小企业 |

三者共用同一颗裸片、同一套策略内核、同一套文档体系。

## 二、GEMV 裸片详细规格

### 2.1 MAC 阵列

```
数量       : 128 颗（预埋派，ADR v0.4 定案）
时钟       : 1.0 GHz
精度模式   :
  bf16     : 每 MAC 每周期 1 op（2B 权重 × 2B 激活）
  int4 SIMD: 每 MAC 每周期 4 ops（2B 打包 = 4×int4 权重）
门控       : 每 MAC 独立 ICG；闲置仅漏电
计算吞吐   :
  bf16     : 128 GOPS
  int4 SIMD: 512 GOPS（等效）
```

### 2.2 存储层次（无 SRAM 架构）

| 层 | 介质 | 内容 | 大小 | 访问者 |
|---|---|---|---|---|
| 寄存器 | 触发器阵列 | 当前激活向量分片 | ~百 B/lane | MAC 直接读 |
| 流式 FIFO | 分布式触发器 | 权重预取缓冲 | 几十 KB | 解码流水线 |
| 片上 ROM | 掩膜/OTP | 权重索引或原始位流 | 按需定制（GB 级可行）| MAC 旁路直读 |
| 外部 NVMe | QLC SSD | 冷模型全量层 | TB 级 | 预取引擎 DMA |

**设计原则：权重是只读数据 → 用 ROM 不用 RAM → 密度 ×10 → 成本 ÷10**

### 2.3 MAC 定标决策记录

| 方案 | MAC 数 | 判定 |
|---|---|---|
| ~~保守派 80-85~~ | 精确配平但无升级空间 | v0.2 推荐 |
| ✅ **预埋派 128** | 面积增量 ≈ die 晶体管 0.2%，MPW 价差 ¥26/颗 | **v0.4 已采纳** |

实验验证：68 vs 85 在脚本中 tok/s 相同——模型盲区已确认；
预埋 128 在当前 8ch 下闲置 33%（门控），未来升级通道时直接解锁。

### 2.4 HBM 结论

三重锁定（PHY 宏 + 版图 + 2.5D 封装），不可后升级。
且 K3 场景为容量受限型，HBM 的带宽密度优势无用武之地。
⇒ **不做 HBM。**

## 三、流式推理架构（核心创新）

### 3.1 原理

MoE 每 token 只激活一小部分专家切片（K3: 25.83 GB/token）。
每层 trunk 工作集实测 **1.17 GB**（93 层 trunk 累计 108.8 GB/token，占总流量 81%）。
⇒ **不需要装下全部权重，只需要及时流过当前层的切片。**

### 3.2 数据流水线

```
NVMe 全量层（¥0.4/GB，QLC 够用）
    ↓ 后台预取（白皮书热度预测算法，88-96% 命中率）
DDR4/LPDDR 落地缓冲（当前层+下一层切片，~2 GB）
    ↓ 解包器（mxfp4 → bf16，移位+scale 乘法）
128 MAC 阵列
    ↓
输出
```

层间切换时零等待：预取引擎提前一层开始搬运。

### 3.3 带宽验证

| 层间搬运量 | 需要的持续带宽 | NVMe 配置 |
|---|---|---|
| 1.17 GB/层（trunk 实测）+ experts | ~400 GB/s（单 token 全层） | 需多盘 NVMe RAID + DDR 缓冲摊平 |
| DDR4 二级缓冲摊平突发 | 有效需求减半 | 6 盘 Gen4 即可 ✓ |

### 3.4 【核心结论】零外挂 DRAM

**流式架构彻底消除了对外部 DRAM 的需求。**

原因：权重不是随机访问的数据——是可预测的顺序流。
每层只流过 ~1.17 GB 切片（trunk 实测均值），预取引擎提前一层开始搬运，
MAC 消费和 NAND 预取在时间上重叠，互不阻塞。

⇒ 不需要 LPDDR5X、不需要 HBM、不需要任何大容量快速存储。
⇒ BOM 中唯一的存储成本 = NVMe 盘（¥0.4/GB），比 LPDDR5X 便宜 200 倍。
⇒ 这就是为什么这个架构在 AI 存储涨价周期中反而更有优势：
   它对存储价格完全免疫——只需要最便宜的 QLC 大容量盘。

### 3.5 【关键突破】DSP 不是必须——加法器替代乘法器

**传统观点：FPGA 上做 MAC 必须用 DSP 硬核。**

实际上，乘法可以分解为移位+加法：

```
a × b = b 次累加 a（或用 Booth 编码 + Wallace 树加速）
```

不同精度的实现成本差异巨大：

| 模式 | 每"乘法器"占用（DSP） | 占用（纯 LUT） | 128 路总 LUT |
|---|---|---|---|
| bf16 | 1 DSP | ~150 LUT | ~19,200 |
| **mxfp4 (int4×int4)** | 1 DSP | **~4 个 LUT6 查表** | **~500** ✨ |

**mxfp4 是最便宜的：**
- int4 × int4 只有 256 种输入组合，输出 7 bit
- 直接做成查找表 ROM，比 DSP 便宜 ~30 倍

**对 Tang Mega 138K（138K LUT / 298 DSP，官方 wiki 数值）的影响：**

| 方案 | MAC 数 | LUT 占用 | K3 吞吐 |
|---|---|---|---|
| 用 DSP（原方案）| 128 | 17% ⚠️ DSP 43% | 0.06 t/s |
| 纯 LUT bf16 | 128 | 30% ✅ DSP 0% | 0.06 t/s |
| 纯 LUT mxfp4-SIMD | 等效 512 路 | 36% ✅ DSP 0% | **0.24 t/s** 🚀 |
| 极限堆叠 | 等效 1024 路 | 65% | 0.5 t/s |

> **口径注（可改用 `pim/calc_fpga_occupancy.py` 复算）**：本表 LUT 占用为**完整 lane 口径**
> （含累加器/接口，~90 LUT/lane，simd_mac_array.v）。若按纯乘核查表口径（12 LUT/lane，
> §3.6 第三步），则 mxfp4-SIMD 仅 ~26%、极限堆叠 ~30%——差异即累加器/控制的代价。
> DSP 占用列：原方案 128/298=43%（官方 298，非历史 192）。
>
> **⚠️ trunk 精度修正（2026-08-29，owner 定案）**：本表「DSP 0%」把**全部层**
> 当 int4 查表——**对 trunk 不成立**。K3 的 trunk（attention/shared/dense/embed/vision）
> 量化质量验证失败，**保留 fp16** →
> - trunk 必须走 bf16/**DSP** 通道：DSP 占用回到 128/298=**43%**，无法归零；
> - SIMD 查表只对专家 int4 有效，对 trunk fp16 实数乘累加失灵；
> - 单 128 MAC 下 LUT 合计 ≈ 39.8%（trunk 128×150 + 专家 512×12 + 固定 29.7K）；
> - 关键：**吞吐受链路带宽限制，不再与 lane 成正比**——见 §3.5.2。
> 复算：`pim/calc_fpga_occupancy.py`（v2，含整链 min(主机NAND, PCIe, DDR3) 与
> 精度分裂面积；K3 流量账 trunk=108.8GB fp16/pass）。

**结论：DSP 从瓶颈变成半空闲。** trunk fp16 需留 128 个；其余 170 个复用为 KV/ECC/激活。
**同样的板卡，吞吐提升 4-8 倍，且不依赖任何 DSP 硬核。**

→ 理论峰值 = 1,333 Mbps × 32 bit / 8 = **5.33 GB/s**（实际含 refresh ~4.3 GB/s）。
这是**板上唯一的容量存储带宽出口**；任何"权重驻留 DDR3"的方案都以它为硬顶。

### 3.5.2 【关键差异】逻辑极限 vs 带宽实顶

**DSP/LUT 是逻辑极限，不是吞吐极限。** 把"极限压榨表"里的 4.2 t/s 正确理解：

| 项 | 数值 | 性质 |
|---|---|---|
| 逻辑极限（9,045 lane，官方 138,240 LUT）| ~4.2 t/s | 受限于 138K 的 LUT，**放得下** |
| ~~带宽实顶（DDR3 5.33 GB/s）~~ | ~~0.2 t/s~~ | ~~单看 DDR3~~（见修正④）|
| **整链带宽实顶（min:主机NAND→PCIe x4→DDR3）** | **≈2.0 GB/s → ~0.077 t/s** | 上游 PCIe/盘才是真瓶颈 |
| 差距 | ~54× | 瓶颈是**上游链路**，不是 DDR3、更不是逻辑 |

**推论**：在 138K 上堆 lane 无意义——喂不饱。**而瓶颈在主机侧的盘→PCIe，
不在板上。** GEMV 的"最大限度用空间"= 逻辑榨干；但纯物理吞吐由链路定：
true_t/s = min(逻辑, 链路) = **链路 ≈ 0.077 t/s**（trunk fp16 常驻 DDR3 口径）；
若 trunk 也全流式（每 token 134.6GB）则该值再降到 ~0.015 t/s。

> **修正④（整链 vs 单环节，2026-08-29）**：早前"带宽实顶 0.2 t/s"只算了 DDR3 5.33 GB/s
> 单一环节。138K 的权重来自**主机侧 NAND（SSD/HDD）→ PCIe Gen3 ×4**，不去板上大 NAND。
> 真实链路 = min(主机盘 2.0≈总盘能力, PCIe x4 ~2.96, DDR3 5.33) = **~2.0 GB/s**。
> 复算：`pim/calc_fpga_occupancy.py`（v2，A 段整链 min 规则）。

> **资源占用复算工具**：`pim/calc_fpga_occupancy.py`
> （官方基线 + 组件成本参数化：LUT/DSP/B-SRAM/带宽/lane 上限/带宽实顶，
>  两套 lane 口径对照，可改参重跑；本节的 9,025 lane 与 4.2 t/s 自此有代码可查）。

### 3.6 【资源复用】空闲 DSP 的再利用与收益量化

> **⚠️ 受 trunk fp16 定案影响（2026-08-29）**：本节的"全部 298 DSP 空闲"是 trunk 也当 int4
> 的旧前提。定案后 trunk 需 **128 DSP 作 bf16 通道**（SIMD 查表对 fp16 失灵），
> 可再分配 DSP = 298 − 128 = **170**。以下三个子系统从 298 预算改从 170 支出。

MAC 改用 LUT 查表后，Tang Mega 138K 上原本 298 个 DSP，**除 trunk 需要的 128 外，余 170 个**。
这些 DSP 不浪费，分配给三个关键子系统：

| 子系统 | DSP 数 | 收益 |
|---|---|---|
| **KV-Cache 量化写回** | 32 | 同样内存下上下文长度翻倍（32K→64K tok）|
| **NAND BCH 纠错** | 16 | 数据可靠性从 ❌ 乱码 → ✅ 硬件级 |
| **激活函数多项式拟合** | 16 | BRAM 省 8%，FIFO 可扩容 32KB |

合计 64，占 170 预算的 38%；剩余 ~106 DSP 留作 trunk bf16 余量与裕度。

#### KV-Cache 收益（以 K3 为例）

假设 hidden=4096, layers=64：

| 上下文长度 | fp16 占用 | Q8 占用 | 节省 |
|---|---|---|---|
| 2K tok | 2.15 GB | 1.07 GB | 50% |
| 8K tok | 8.59 GB | 4.29 GB | 50% |
| 32K tok | 34.4 GB | **17.2 GB** | 50% |

⇒ 32GB DDR 板卡：fp16 只能跑 32K，Q8 可以跑到 **64K**。

#### NAND ECC 的必要性

- QLC 原始 BER ≈ 1e-3，不加纠错基本不可用
- 用 DSP 做 BCH(8192,7680) 纠错，吞吐需求 <10 µs/block ✓
- 没有这一项：NAND 读出的数据是坏的，推理结果就是乱码

#### 结论

> 吞吐不变（MAC 数没变），但"能跑"和"能用"的差距：
> - 没有 ECC → NAND 读出数据坏
> - 没有 KV 压缩 → 长上下文 OOM
> - 没有 BRAM 余量 → FIFO 瓶颈
>
> **DSP 复用不是锦上添花——是把原型变成可用产品的必要条件。**

### 3.7 【核心突破】资源复用 → 吞吐倍增完整推演

前三节的结论串起来：

1. MAC 用 LUT 查表替代 DSP → **省下 DSP**
2. DSP 复用做 KV/ECC/激活函数 → **省下 LUT**
3. 省下的 LUT 全部换算成更多 MAC → **吞吐暴涨**

#### 第一步：DSP 复用释放的 LUT

| 被替代的功能 | 原 LUT 占用 | 改用 DSP 后 |
|---|---|---|
| 激活函数 SiTU-GLU | ~2,000 | 0 |
| KV-Cache 量化 | ~800 | 0 |
| NAND BCH ECC | ~3,500 | 0 |
| **合计释放** | **~6,300** | |

#### 第二步：释放的 LUT 换算成 MAC

每条 mxfp4-SIMD 通道成本 ≈ 12 个 LUT（查表+分摊累加器）。

| 方案 | 新增通道 | 总通道数 | 加速比 | K3 吞吐 |
|---|---|---|---|---|
| 原方案（DSP 做 MAC）| — | 128 MAC | 1× | 0.06 t/s |
| LUT 替代 DSP | — | 512 lanes | 4× | 0.24 t/s |
| + 复用释放的 6K LUT | +525 | **1,037** | **8×** | **0.49 t/s** 🚀 |

#### 第三步：极限压榨

把板上所有非固定开销的 LUT 全部换成 mxfp4-SIMD 通道：

| 项目 | 数值 |
|---|---|
| 板上总 LUT (Tang Mega 138K) | 138,000 |
| 非 MAC 固定开销 | ~29,700 |
| 可用于 MAC | 108,300 |
| 最大通道数（÷12，全查表）| **9,025 条**（仅专家 int4 时可行）|
| 相对原方案加速比 | **17.6×** |
| **理论最大 K3 吞吐** | **≈ 4.2 t/s** 💥（纯逻辑极限）|
| ⚠️ **整链带宽实顶（修正后）** | **≈ 2.0 GB/s → ~0.077 t/s**（上游主机盘→PCIe x4）|

> **⚠️ 校准提示（2026-08-29，修正④）**：本表 4.2 t/s 为**纯逻辑极限**（LUT 放得下 9,025 条 lane），
> 不是真实可达。138K 权重来自**主机侧盘→PCIe Gen3 ×4**，整链瓶颈 =
> min(主机盘 ~2.0, PCIe x4 ~2.96, DDR3 5.33) ≈ **2.0 GB/s**；
> 按 K3 每 token（trunk fp16 常驻时 25.8GB）换算 → **带宽实顶 ≈ 0.077 t/s**。
> 且 9,025 条 lane 全查表方案需 **trunk 也 int4**——trunk 已定案保 fp16，
> 故 trunk 部分必须走 bf16/DSP，该 lane 数实际不可达（见 §3.5 修正块）。
> 差距 ~54×：138K 的 GEMV 瓶颈是**上游链路与 trunk 精度**，不是逻辑密度。

### 3.6 官方 K3 技术报告架构要点（2026-08-27 读取）

> 来源：`kimi-k3-tech-report.pdf`（47 页）+ arXiv:2607.24653

**核心参数对照表（K2 → K3）：**

| 参数 | K2 | K3 | 变化 |
|---|---|---|---|
| 总参数 | 1.04T | 2.78T | +167% |
| 激活参数 | 32.6B | 104.2B | +220% |
| 层数 | 61 | 93 | +52% |
| 注意力组合 | 61 MLA | 69 KDA + 24 MLA | 混合注意力 |
| 路由专家数 | 384 | 896 | +133% |
| 每 token 激活专家 | 8 | 16 | +100% |
| 共享专家 | 1 | 2 | +100% |
| 隐维度 | 7168 | 7168 | = |
| Latent MoE 维度 | — | 3584 (0.5×) | 新增 |
| 专家隐维度 | 2048 | 3072 | +50% |
| 注意力头数 | 64 | 96 | +50% |
| 激活函数 | SwiGLU | SiTU-GLU | 改进 |
| 量化 | — | MXFP4 权重 / MXFP8 激活 | QAT 训练 |

**架构关键发现（对 GEMV 设计的影响）：**

1. **块结构**：每个块 = 3 KDA + 1 Gated MLA，各配一个 Stable LatentMoE FFN
   - 93 层 = 69 KDA + 24 MLA = 93 个 FFN
   - KDA = delta-rule 递归状态（固定大小，无 KV 缓存增长）
   - MLA = 标准 KV 缓存（低秩压缩，随序列增长）

2. **Stable LatentMoE**：2 个共享专家（全宽7168）+ 896 路由专家（latent 3584）
   - 路由专家每 token 激活 16 个
   - Quantile Balancing：推理时冻结路由偏置，无需辅助损失
   - 每个路由专家 SiTU-GLU FFN：gate_proj + up_proj + down_proj，各 3584×3072

3. **AttnRes（注意力残差）**：每层有学习的伪查询（w），计算对所有前序层输出的注意力权重
   - 需要保留所有 93 层的输出（O(Ld) 内存）
   - 对 trunk 内存预算有直接影响

4. **推理优化**（§5.4）：
   - 前缀缓存：物理块 6144 token，哈希块 512 token，KDA 检查点在哈希边界保存
   - MoE 解码：token 中心的流式内核（WarpDecode 风格），每个 warp 流式读取一个专家权重
   - Latent GEMM：路由器 + down_proj 融合为一个 GEMM；latent 矩阵跨 rank 分片
   - **无 SSD/PCIe 流式推理**——这是我们的创新空间

5. **量化确认**：MXFP4 权重 / MXFP8 激活是 QAT 训练的原生格式
   - 专家权重已是 MXFP4，无需后训练量化
   - trunk 未做 QAT（官方 trunk-quantisation.txt 确认 int4=17.4% 误差）
   - **我们的 mxfp4 trunk A/B 实验也证实**：cosine=0.8848, top1_match=False → trunk 不能量化

6. **流量分布实测修正**：
   - 原始声称 trunk ≈ 280 MB/层 → **实测 1.17 GB/层**（4.2× 低估）
   - trunk 总流量 108.8 GB/token（81%）vs experts 25.8 GB/token（19%）
   - 修正后单 token 全层带宽需求：~134.6 GB（bf16 trunk）或 ~53 GB（mxfp4 trunk 假设）

7. **SINKER 存储设计启示**：
   - 官方在集群规模（H20/H100 + NCCL）解决带宽问题
   - 我们的单 GPU + NVMe SSD 架构是完全不同的部署层级
   - KDA 固定状态 + MLA KV 缓存的混合设计验证了我们的流量模型
   - Token-centric WarpDecode 内核验证了流式权重消费的可行性

## 十二、带宽恒定下的吞吐榨取策略

> 前提：算力(63 t/s 等效) > 存储带宽可支撑的量(~50 t/s)。
> 此时提升吞吐的思路从"传快点"转为"少传"或"一字多用"。

### 12.1 投机解码（救单聊延迟）

小草稿模型连猜 k 个 token，大模型一次前向同时验证——
权重只读一遍，产出 ~k 个 token。

| 场景 | 现在 | 加投机解码 (k=4, 接受3) |
|---|---|---|
| batch=1 单聊 | 0.14 t/s | ~~~0.42 t/s（×3）~~ 见下修正 |

**【实测修正 · T3】相邻位置专家集重叠率 ρ = 0.279 ± 0.05**（92 层微平均，
真实轨迹 67 对相邻位置）。代入本框架 U(k)=1+(k-1)(1-ρ)：
U(2)=1.72、U(4)=3.16 ⇒ 流量口径加速上限 **k/U ≈ ×1.16~1.26**。
MoE 专家流量稀释把"×3"压到 ~×1.26，且接受率还会再打折。
投机解码对 K3 单聊仍有小赚，但不再是主要杠杆。

草稿模型足够小，可直接跑在板载 RISC-V AE350 上。

### 12.2 热专家缓存（救批量吞吐）

MoE 专家访问呈重尾分布（项目前作预测命中率 88-96%）。
板上 1GB DDR3 常驻最热专家切片，命中读取不占 SerDes。

**【勘误 v3 · 真实拓扑终审】k3-verdict.md 实测参数（92层×896专家×top16，切片17.55MB）代入后：**
热集 = 92×16 切片 ≈ **25.8GB ≫ 1GB**。合成 Zipf s=1.0~2.5 全档实测 LRU 命中 **0.6~2.2%**。
⇒ 单卡热专家缓存路线对 K3 正式关闭；吞吐收益 ×1.02。
翻案唯一路径：≥32 卡专家分片使每卡工作集 <1GB。

**【勘误 v4 · 真实轨迹复跑（T3，2026-08-26）】v3 被真实数据推翻，路线复活：**

数据源：引擎真跑遗留的 `expert_trace.bin`（2026-08-18，1 条 prompt × 68 位置 × 92 层 × top16
= 100,096 条真实请求；分析脚本 `t3_tools/small_cache.py`、`t3_tools/rho_real.py`）。
⚠️ 样本量 n=1 prompt，结论待更大样本复核。

实测：
- 路由高度集中：**90% 请求是重复访问**；仅触及池子 12.14%（10,010 个专家 ≈ 175.65 GB）；
  最热切片 L4/e520 被 68/68 个位置全选 —— "热门的路" 真实存在
- 板级预算下的 LRU 命中率：**1GB=35.3%、2GB=36.2%、8GB=36.2%、128GB=49%**
  （Belady 上限：64GB=61.7%）⇒ SerDes 有效收益 **×1.55**（非 v3 的 ×1.02）
- 但注意机制：90% 复用率主要是"16 选自 ~109"的饱和效应，相邻位置集合重叠仅 ρ≈0.28
  （见 §12.1 修正）——集中是真，强时间局部性未必真

**【框架修正 · 缓存的对象是路由路径，不是热门专家】**

热度分级缓存只是兜底。主策略是**路由驱动预取**：
- router 权重极小（每层 gate [896×7168] bf16 仅 12.85MB），随 trunk 流提前一层读入
- 层 L 的输入一就绪即可算出层 L 的完整路由（batch 内全部位置），
  ⇒ NVMe 预取引擎沿"已知的路径"搬运层 L+1 的切片，命中是确定性的，不依赖统计
- 此时 DDR3 的角色退化为流水线缓冲（容量 ∝ 预取窗口 × 17.55MB），不再是按热度驻留的仓库
- 冷读地板（任何策略都躲不开）：每条新文本必读的不同专家 ≈ 10k × 17.55MB ≈ **2.58 GB/token**（实测）
- 兜底场景（路由尚不可知、或跨文档驻留）：才轮到频率式热路径缓存，价值即上面的 35%@1GB

**【实验复核 · 同日】对上面框架的三项检验（`t3_tools/audit_layout.py`、`replay_sim.py`）：**
1. **"专家块散装"证伪**：审计 96 分片全部头信息，被触及的 10,010 个专家
   全部是单文件内单一连续块（6 张量零缝隙）——checkpoint 布局比预想健康，无需整块化改造
2. **"重排打包"伪需求**：以预取窗口模型模拟三种摆放，当前 checkpoint 编号序
   在深度 256 切片（≈4.5GB 窗口）下全程仅需 **2,085 次**窗口重开（覆盖 10 万次访问）；
   按全局频率重排反而恶化到 72,956 次 —— 训练形成的专家编号天然共现聚集，
   任何人为重排都是破坏
3. **"预知替换"增益集中在极小预算**：Belady−LRU 差 = +23.8pt@0.25GB、+5.1pt@0.5GB、
   **仅 +1.2pt@1GB** —— 路由计划的替换价值随预算增大而消失；
   其不可替代的价值在**调度**（提前知道 miss ⇒ 大批量顺序搬运、隐藏延迟），不在命中率
⇒ 修订结论：数据结构本身没有低成本可摘的果子；收益方向 = 小预算板上的路由计划 +
   沿既有布局的顺序批量预取，而不是重组 1.45 TB。


**【勘误 v2】模拟器实测（tools/hot_expert_cache_sim.py）推翻下表预期：**

K3 形状下热专家全集 ≈ 3.8GB（top-2×64 层×30MB）≫ 板上 1GB，
合成 Zipf 轨迹（s=1.0~2.0）实测 LRU 命中仅 **10~15%**，
吞吐收益仅 ×1.15 —— 远低于下表幻想值。

原表保留作"若命中可达时"的参考上界：

| 命中率 h | 有效吞吐 |
|---|---|
| 15%（实测天花板）| ~58 t/s |
| 50% | ~100 t/s |
| 80% | ~250 t/s |

缓存真正起飞的两个前提：
① 真实负载有强域偏好（需 K3 真实路由轨迹验证，工具已就绪）
② 多卡按专家分片，每卡工作集缩小到 DDR3 可容纳

### 12.3 线上压缩（已封存 2026-08-29）

> **定案：压缩路线整体关闭。** trunk 量化已否决（保 fp16，B.9-B.12 + k3-verdict §八）；专家侧 25.83GB/token 是字节硬账（B.20），熵编码/BF8 微省 % 级，换不来量级收益，不再投入。以下为历史记录，仅作参考上界。

- scale 差分：E8M0 相邻块常相同 → 省 ~4%
- E2M1 熵编码：零值/小幅值占比高 → Huffman 再挤 10-15%
  （FPGA 解码只需一张小查找表）

### 12.4 模型侧瘦身（已封存 2026-08-29）

> **同样封存。** 混合精度 95% 层 int4 已被 B.9 否定（trunk 4-bit 重建误差 17.4%）；收紧 top-k / 早退属于质量换带宽，且 K3 已到 top-16 下限（B.13 后口径），不构成主方向。

- 收紧路由 top-k（如 8 选 2 → 8 选 1.5）
- 早退层：简单 token 提前输出
- 混合精度：95% 层 int4 + 5% 敏感层 bf16

### 12.5 组合结论

```
延迟线：投机解码   上限 ~×1.26（ρ=0.28 实测，§12.1）—— 大幅低于本节初稿的 ×3
吞吐线：路由驱动预取（主）+ 热路径兜底 ×1.55@1GB（勘误 v4）
两线正交，可叠加。
```

## 十三、独立运行固件架构（RISC-V 控制面）

> 独立盒子 = Pro 板 + M.2 盘 + RISC-V 上的"掏心版" kimi-k3-in-c。
> RISC-V 不做推理，做指挥。

### 13.1 职责划分

```
kimi-k3-in-c 原版（纯 CPU）：
   读 GGUF → 循环每层 → 【C 语言算所有矩阵乘】→ 输出
                          ↑ 在 720 MIPS 上会慢死

移植版（板载骨架）：
   读 NVMe 权重流 → 循环每层 → 【写寄存器触发 MAC 阵列】→ 输出
                                ↑ 数学内核掏空，换成硬件调用
```

### 13.2 分工与开销

| 组件 | 职责 | 开销 |
|---|---|---|
| **RISC-V AE350** (~720 MIPS) | tokenizer、采样、KV 记账、路由 softmax、预取命令、层循环控制 | ~10-50ms/token |
| **MAC 阵列** (1,258 lanes) | 全部大矩阵乘（专家 FFN） | ~7s/token（带宽决定）|
| **DSP 复用单元** | SiTU-GLU、KV 量化 | 流水内隐藏 |

**【实测修正 · T3】"路由 softmax ✅ 微秒级"不成立：**
router 是 [896×7168] GEMV，每 token 每层 6.4M MAC × 92 层 ≈ 1.18 GFLOP/token。
RISC-V 标量 @720MIPS ≈ **1.6 s/token**，超预算 30 倍以上。
⇒ 路由 GEMV 必须也走 MAC 阵列（128 lane ÷ 6.4M MAC ≈ 50µs/层 ≈ 4.6ms/token ✓），
或 int8 SIMD；RISC-V 只做 top-16 选择与记账。

控制面开销占比 <1%。慢的依然是带宽——但全程无主机参与。

### 13.3 内存可行性（RV32 + 共享 1GB DDR3）

```
tokenizer 词表        ~几十 MB        ✓
隐藏状态缓冲          每 token 8KB    ✓
logits 缓冲           ~600KB          ✓
权重                  ❌ 不驻留 —— 本来就是流式的
```

**关键自洽：正因为架构是流式设计（权重从不驻留），
"小内存控制器 + 大模型"的矛盾根本不存在。**

#### T1 · 解码打包格式 ✅ 已完成（2026-08-26，产出 `notes/k3_pack_format.md`）

- 前置：无（k3_index.json 已在盘上）
- 操作：
  1. 从任一 safetensors 分片抽 1 个 expert 的 w1 weight_packed 张量
     （形状 [3072,1792] U8，逻辑宽度 = 1792×2 = 3584）
  2. 取前 4KB 导出十六进制 + 对应 weight_scale 前 256B
  3. 尝试常见打包假设并校验：
     a. ~~每 U8 装 4 个 2bit 码~~ → 排除（码全非负、分布 29.8/23.0/28.1/19.1%，
        无法解释权重正负对称性）
     b. **每 U8 装 2 个 4bit E2M1** ✅ → 定案，即 OCP MXFP4
     c. 位平面切分（bitplane）布局 → 排除
  4. 用 group=32 的 E8M0 scale 反量化一组 32 权重验证
     （nibble 分布吻合 E2M1 码表统计，解码后 15 值对称、mean≈-0.08）
- **定案**：`value = E2M1[nibble] × 2^(scale-127)`，nibble 低=偶/高=奇，
  scale 每 32 元素 1 个（`K3_MXFP4_GROUP=32`），255=NaN→0。
  每元素 0.5+1/32 = 0.53125 B → expert 17,547,264 B 与裁决一致。
- 产出：`notes/k3_pack_format.md`（位序/字节序/组内排列的最终定义）✅
- 回填：`rtl/12_fpga_proto/rtl/simd_mac_array.v` 的解码查表（E2M1 表 16 项）、

 ### 14.2 板卡机（Tang Mega 138K 到手后）

> **硬件节点（2026-08-27）：二手 Tang Mega 138K Pro，¥850 入手。**
> Pro 版相比原版资源更多（GW5AST-138，LUT/BRAM 有提升），
> 上板前先做收货验收（见下），再按 T5→T6→T7 推进。
> 后续需补购 NVMe 硬盘（容量选择见 §2.2 存储层 / §14.4）。

> **结构拆解里程碑（2026-08-27）：MoE「先路由后搬运」在 K3 上成立的实锤。**
> 来源：sglang `python/srt/models/kimi_linear.py` + `kimi_k3.py` 源码。
> **关键事实 —— router 与 experts 吃同一个 hidden_states：**
> ```
> router_logits, _ = self.gate(hidden_states)
> final_hidden_states = self.experts(hidden_states, topk_output)
> ```
> - `gate` = `ReplicatedLinear(7168 → 896)`，权重仅 7168×896 ≈ 6.4M 参数，
>   **可完全常驻内存（几十 MB）**
> - `experts` 也吃同一个入层 `hidden_states`
> - **结论：可以「先算 router（极小常驻权重）→ 拿 top16 → 再精准搬运那 16 个专家」，
>   把「整层读 896 专家」变成「只读 top16」**
> - 绕不开的部分：本层 router 依赖本层注意力输出（KDA/MLA 权重须先算）；
>   要躲开它只能退到「用上一层 h 预测本层路由」，命中率非 100%
> - 待办 T8：据此写 `expert_extractor.py` 实测「先路由后搬运」能把搬运量压到多少

> **T8·实测里程碑（2026-08-28）：专家侧已到理论下限（expert_extractor.py）。**
> 用真实 100K 条路由轨迹 + 17.55MB/专家实测参数：
> ```
> 整层读 896          : 1412.8 GB/token
> 先路由只读 top16    :   25.2 GB/token  （省 98.2%，与 k3-verdict 25.83 吻合 98%）
> +1GB LRU(命中35.4%) :   16.3 GB/token
> ```
> **反直觉结论：现成引擎本来就是「先路由后搬运」了，专家侧只读 1.79%(16/896)，
> 已到理论下限，不是瓶颈。剩余可捅破空间在 trunk。**

> **T10·里程碑（2026-08-28）：trunk「精度黑洞」—— 下一道真正的墙。**
> waste K3.md 源码实锤：**trunk 除 routed experts 外全为 bf16(16bit)，
> 只有专家用 MXFP4(2.12bit)**。
> - 专家（MXFP4 只读 top16）：25.83 GB/token
> - trunk（bf16 → 用户量化 36GB）: 36 GB/token
> - **trunk 占每 token 61.8GB 的一半以上，却是 16bit；专家仅 2.12bit →
>   精度杠杆看似没榨干**
> - ❌ **但实测否决：trunk 内大 shape（full-rank 密集矩阵）低精度压缩不可行**
>   （真实权重量化后质量崩坏）。压不动的不是「trunk」标签，而是大而密的
>   shape；专家能压 2.12bit 是因为小 shape 块(17.55MB/个)对 MXFP4 有效
> - **待查 A**：bf16 重建 trunk 91.45GB 只对齐 110GB 的 ~83%，
>   剩 ~23.88GB 账目缺口（非压缩方向，仅账目核对）
> - **现实底线：trunk 36GB 压不动，每 token 61.8GB 是底线；专家已到 top16 下限**
> - **▶ 定案（2026-08-29）：采纳 36GB 压不动之结论 → trunk 保留 fp16，
>   流量账 trunk=108.8GB/pass（见 k3-verdict §八修订，36GB 口径作废）。
>   对 138K 资源的连锁影响见 §3.5 修正块与 §3.6（DSP 占用回 128/298）。**

### B.11 符号位必要性 + trunk 精度阶梯定案（2026-08-28 续）
**用户问：权重为何需要符号位？可否全正数？**
- GEMM `Σ W·x`：W 符号决定增强/抑制，是表达能力必要部分；K3 权重元素正负约各半（平衡点 0）
- 无符号存储 `U=|W|` 丢失信息→崩；符号位是信息载体，不可省于权重量化
- 用户的直觉对应真机会（记录备用）：**权重平衡化 weight-balancing**——按行乘符号向量预平衡成多数为正 + 对称激活，推理时恢复符号；对 4bit 存储才划算（符号位占 1bit），对 BF8 收益小；且对已知非负的激活（SiTU-GLU 输出等）天然可无符号。待后续评估。

**trunk 精度完整阶梯（full_moe_trend.py，4层 dense 残差链，norm=on）**：
| 层 | BF8-E4M3 | BF8-E5M2 | MXFP4-E2M1(2bit) | KM-4b(4bit) |
|----|----|----|----|----|
| 1 | 25.8 | 21.4 | 12.8 | 12.0 |
| 2 | 22.1 | 17.7 | 9.7 | 7.8 |
| 3 | 19.5 | 15.2 | 7.2 | 4.3 |
| 4 | 18.5 | 14.2 | 6.4 | 1.6 |

- **E4M3 优于 E5M2**（每层 ~4dB）：K3 trunk 权重值域有界(±448内)，永远吃不到 E5M2 的大指数范围，却要付尾数精度损失 → **选 E4M3**
- **MXFP4-E2M1(2bit) 4 层崩到 6.4dB**，与 KM-4b(1.6dB) 同属"4bit 级"，均**不可用于 trunk**
- **为什么专家能 MXFP4 而 trunk 不能【核心规律】**：路径结构决定容忍度——trunk 的 down/up/shared 是每层必走全宽密集投影、**残差直通**，4bit 误差无衰减累积；专家是**稀疏路由+latent窄空间+非残差直通**，4bit 误差不沿 dense 链累积。官方 trunk=BF16/专家=MXFP4 正是此规律的设计体现（且实测 trunk 可降到 BF8-E4M3，官方 BF16 偏保守）
- **定案：trunk → BF8-E4M3（4层18.5dB，省一半空间）；专家维持 MXFP4**。不再支持更高压缩
  - ⚠️ **被 8-29 定案推翻**：owner 最终定案 trunk 保 fp16，本节"BF8 定案"作废，仅存档。
  - 佐证：8-29 真 K3 张量分解实测（kda-mla-decompose §19）显示 qkv/trunk 满秩墙，量化省空间方向无收益，与保 fp16 一致。

### B.14 "算得快"实测：单token GEMV vs 批次 GEMM（2026-08-28）
down_proj 形状 [3584,7168]x[7168,3072]，k3 16线程 fp64→实测（fp64为稳妥计时）：
| batch | 每op ms | 聚合 TFLOPS | 每token ms |
|----|----|----|----|
| 1(GEMV) | 10.31 | 15.3 | 10.31 |
| 4 | 17.52 | 36.0 | 4.38 |
| 16 | 28.28 | 89.3 | 1.77 |
| 64 | 78.27 | 129.1 | 1.22 |
| 256 | 303.7 | 133.0 | 1.19 |
- **单token GEMV 极慢**（10.3ms/个down_proj）因为算术强度低、memory-bound、算率仅15TF
- **批次化 = 算得快解药**：batch256 → 每token 1.19ms（8.7x），聚合算率 15→133TF（硬件饱和）
- 模型规模：单层~10个大矩阵 down/up(2)+shared(3)+attn(5)，93层≈930次大乘 → batch256 时全层 ~1s/token 计算（勉强可用）
- ⚠️ **核心矛盾**：批次化救计算侧，但传输侧每token字节不变——除非权重驻留内存跨批次复用。真正方案=**权重驻留+批次复用**（驻留DRAM的权重跨token共享，只搬批次间增量）

### B.15 "传得快"完整决策表（真实字节×带宽×批次，实测data）
- 真实 /model = **1.6TB**（1.67e12 B，93层全权重+MXFP4专家打包）
- trunk BF16 = 1248MB/层 ×93 = **116GB**（纯维度算）；BF8=58GB；4bit=29GB
- 传输时间 @ 纯单token全扫 = 字节/带宽：
  | 带宽 | 全模型1.6TB | BF16 trunk 116G | BF8 trunk 58G |
  |---|---|---|---|
  | 1.5GB/s SATA | 1067s (~18min) | 77s | 39s |
  | 7GB/s NVMe | 229s | 17s | 8s |
  | DRAM 50GB/s | 32s | 2.3s | 1.2s |
- **结论：单token全量流式在任何当前内存层次不可行**（最低也是秒级/token）
- **必须批次+驻留**：批次分摊计算（B.14），驻留使权重跨token复用不重传 → 传输时间=驻留外增量/带宽，可到实用级
- 决策杠杆排序（按收益）：① 批次化（计算8.7x+传输分摊）＞② 权重驻留DRAM（消除重传）＞③ 更高带宽存储 ＞④ 量化降字节（BF8/4bit补充）

**目标转向落定**："算得快/传得快" = 批次GEMM(计算饱和) + 权重驻留(传输消除重传) + 量化(降字节辅助)。SNR 研究停止，以实测带宽/算率为准。
### ⚠️ B.16（已被 B.18 证实为假象纠正）决定性突破：并发预取使"传得快"从死路变可行（2026-08-28）
**背景**：单线程 dd 冷测 /model 仅 45-58 MB/s，一度判定"k3 跑不动 MoE"（死路）。
**真相**：那是 **WSL 虚拟盘单请求延迟假象**，非存储硬限制。并发预取式读（2/4/8 线程并行，首 2GB）：
| 线程 | MB/s |
|----|----|
| 1 | 58 |
| 2 | **6480** |
| 4 | **8379** |
| 8 | 7656 |
- **2 路并发即 6.5GB/s，4 路 8.4GB/s —— 提升 140 倍**
- 结论：**流式推理必须并发预取（≥4路）+ I/O/计算重叠**，带宽不再硬天花板

**修正后的流式预算 @8.4GB/s**（每 token 激活视图）：
| trunk | 全93层/token | batch64 | batch128 |
|----|----|----|----|
| BF16 116G | ~164GB | 0.31s | 0.15s |
| BF8 58G | ~107GB | 0.20s | 0.10s |
- 从"45MB/s 分钟级/token"修正为"8.4GB/s 下 0.1-0.3s/token"（batch 到位）
- ⚠️ 计算侧（B.14 实测 batch256 全层 ~1s）此时**可能反成新瓶颈** → 需验证流水线重叠后的真实端到端

**架构定式**：并发预取（多路读当前层+预取下层）→ 批次 GEMM（权重在内存跨 batch 复用）→ 层内 I/O/计算流水线重叠。26GB 内存不足驻留多层 → 逐层流水线（预取→算→释放→预取），而非整模型驻留。
### ⚠️ B.17（继承 B.16 假象前提，已被 B.18 作废）端到端流水线模拟：k3 跑起来的诚实极限（2026-08-28）：用全部实测常数构造 stream_sim.py（93层，并发预取8.4GB/s + 批次GEMM重叠，max(io,comp)流水线）。
| trunk | 每层I/O | 每层计算 | 93层端到端 |
|----|----|----|----|
| BF16 | 211ms | 1-5ms | 19.7 s/token (0.051 tok/s) |
| BF8 | 137ms | 1-5ms | 12.8 s/token (0.078 tok/s) |
- 瓶颈 = I/O（预取一层 211/137ms），计算被完全吸收（1-5ms），batch 不帮助：token 各自流式搬权重（26GB内存装不下驻留），batch 只加速已非瓶颈的计算
- 结论：k3 上 MoE 流式推理端到端 = 10-20s/token（BF8/BF16）——能跑通（架构验证OK），但不够实用
- 唯一真优化杠杆 = 减少每层字节：BF16→BF8 省 50%；深量化（B.11）排除；k3 虚拟盘 8.4GB/s 已是内部最快，更高带宽收益有限
- 实用化出路（超出k3当前硬件）：更大内存驻留多层 / GPU后端 / 更大batch硬件

交付：stream_sim.py 为可复现端到端模拟器；prefetch_bw.py/gemv_vs_gemm.py/byte_budget.py/flow_budget.py 为实测常数来源。

**探索结论：`kimi-k3-in-c` 的流式 C 实现早已完整且成熟**，无需从零新写：

**⚠️ B.16 的重大假象纠正（推翻早前结论）**：
- 早前"8.4GB/s 并发预取、提升 140 倍"是**假的**：`prefetch_bw.py` 在 1/2/4/8 线程之间**没有 drop_caches**，后几次跑分是**页缓存命中**（内存驻留），非磁盘带宽

### B.19 trunk 放错盘：SINKER sdd7 vs /model 实测差 31 倍 + 持久挂载破解（2026-08-28）

**用户洞察**：k3 的 `/model` 是 VHDX 虚拟盘（sde，100% 满，60MB/s 墙），而 k3 有**真实物理盘 SINKER（PHYSICALDRIVE2, SEV512THK 476.9GB SATA SSD）**。trunk 一直放错盘——慢盘上挣扎，快盘闲置。

**实测真实带宽（严格冷缓存，O_DIRECT）**：
- `/model`（sde VHDX）：55-77MB/s 平坦墙（B.18，无论并发/O_DIRECT/布局都打不破）
- **SINKER /dev/sdd7 裸块设备读**：单线程 1013MB/s，**4线程 1889MB/s**（8线程 1735MB/s）
- SINKER 写：735MB/s（dd 实测，符合 SATA 3.0 极限）
- ⚠️ 修正早前"8.6GB/s"是文件系统路径的 **ext4+页缓存/宿主缓存假象**；裸设备读 ~1.9GB/s 才是物理真实

**端到端预算（trunk 放 sdd7，4线程 1.9GB/s）**：
- 108.8GB / 1900MB/s ≈ **57s/token**（vs /model 的 1663s/token，**~29 倍**）

**持久挂载破解（关键）**：
- 根因：`wsl -e bash` 命令结束**VM 就关闭**，挂载随 VM 消失 → 每次挂载都丢
- 解法：**让 k3 VM 常驻**（后台 `nohup sleep 86400` + 内核级 `mount /dev/sdd7 /mnt/wsl/PHYSICALDRIVE2p7`）→ 跨命令保持
- 已验证：VM 存活时，另一 `wsl -e bash` 调用来/相见挂载仍在（/proc/mounts 显示 sdd7 已挂）
- `wsl --mount` 报 `WSL_ALREADY_MOUNTED` 不可用；`Set-Disk -IsOffline $false` Access Denied 不可用；只能 WSL 内 `mount /dev/sdd7`
- **非持久前提**：Windows 重启 / `wsl --shutdown` 后需重跑 `k3-mount.bat`（已建 H:\k3\k3-mount.bat）
- 引擎指向：`k3 <model_dir> --trunk /mnt/wsl/PHYSICALDRIVE2p7/trunk`（k3_trunk.c 读 <dir>/trunk.json + trunk.bin）

**落地**：102G trunk 从 /model 拷到 sdd7/trunk（源 sde 慢盘 60-80MB/s 读 → 拷贝 ~25 分钟），待完成后 k3_run 验证 s/token 是否从 1663 降到 ~57 区间。

### B.20 L2 专家缓存实测：sdd7 256GB 冷/热缓存 verdict + gen=32 长跑（2026-08-28~29，H:\k3）

**背景**：sdd7 是真实物理 SSD（SEV512THK SATA，裸块读 1.9GB/s，B.19），`trunk` 放 sdd7 后，额外开出 `experts.l2`（256GB）给专家切片做跨 token 二级缓存。引擎新增 `--l2 FILE --l2-gb N`（kimi-k3-in-c，H:\k3\kimi-k3-in-c）。

**8-28 四步修复链（L2 从错到对）**：
- buggy open-addressing find：hit 0.73%，**输出错误**
- pad-fix only：hit 6.67%，输出正确
- pad + slot_of direct map：hit **33.08%**，输出正确（`generated_ids` 命中 [250,3502,123,343]）

**8-28 gen=4 verdict（`/root/k3_l2_verdict.txt` 存档）**：

| 配置 | s/token |
|---|---|
| L2 256GB（slot_of fix, 18:22 bin） | **346.85** |
| no-L2 baseline（iso1, 17:38 bin） | 353.31 |
| intrace old-bin ref | 326.55 |

- L2 报告：requests 5565，hits 1841 (33.08%)；read 32.30GB + written 71.01GB

- I/O share of wall：**112.2%**（trunk 387.8s + experts 1168.5s / 1387.4s）→ 专家 I/O 是绝对天花板

**8-29 gen=32 长跑（进行中，验证跨 token 稳态）**：`--l2 experts.l2 --l2-gb 256 --gen 32`，复用 8-28 已填充的 L2 文件避免冷启动。STEP 表显示 CACHE HIT 稳定 **100%**（token≥5 后专家全命中），但每 token READ GB 恒定 **25.83** —— 专家流量 25.83GB/token 是字节硬账，L2 命中只能省随机读的 seek，省不掉字节本身（25.83GB = 92层×top16×17.55MB）。
