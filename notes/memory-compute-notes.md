# 内存计算设计笔记（对话记录）

> 2026-08-16 讨论沉淀。主题：把 flat-row 算法的成果迁移到内存计算侧，
> 以及"多级置信度数据用于预取/预测"的可行性与现状。

## 点1：flat-row 内核 → 内存计算，可复用的三样"算法级"成果

AVX2 指令本身过不去（PIM/CIM 不跑 x86），但三样东西是内存计算的命门：

1. **精度结论 = 内存计算的规格书**
   - fp32 累加才够（maxrel 1.16e-6）
   - E2M1×2^(sb-127) 在 bf16 无损
   - 激活噪声 1.8e-3 可接受（≈MXFP4 量化噪声）
   - 模拟 CIM 精度比 CPU 差，这组数字就是它必须满足的精度契约。

2. **尺度折叠的布局思想**
   - 组是 16 倍数时把 E8M0 折进 E2M1，去量化走纯整数路径
   - 换到内存侧 = 权重+尺度怎么排进 crossbar/DRAM 行，让近内存计算外围逻辑最少
   - 同一个"位怎么摆、路径怎么变便宜"的直觉。

3. **位精确验证方法论**
   - 去量化结果与参考实现逐位相同的那套纪律
   - 内存计算要采信，必须过"对标参考实现"这关。

**PIM 只算专家 matmul；gate/注意力/残差/尺度应用/部分和累加全在 CPU 侧**
→ 内核今天就可用在"PIM 旁边"，不必等硬件。

### 点1 已落地：`pim/` 参考内核模块
- `pim/README.md` —— 边界规格：PIM 只算 `y[out]=Σ dequant(W)·x`（专家权重
  GEMV），host 保留路由/注意力/残差/GLU/部分和；跨设备只走 k 个 fp32 向量。
- `pim/mxfp4_gemv.{h,c}` —— 独立内核，无 k3.h 依赖，自带 E2M1/E8M0 表；
  求和顺序逐字复刻 `k3_matmul_mxfp4`（按 group 展开 → 8 累加器
  ((s0+s4)+(s1+s5))+((s2+s6)+(s3+s7)) → 尾 fma → group 尾乘 scale → double acc）。
- `pim/verify.c` + `make_fixture.py` —— 真实 checkpoint 字节逐位验证，**全 PASS**：
  ① dequant == fixture expected ② GEMV == 参考核（zeros/ones/alt/rand/small/
  special 含 NaN/inf）③ nibble 交换对抗（顺序是载重语义）。
- `make verify` 一键：转换 fixture → 编译 → 断言。
- `make measure`（`pim/sim_cim.c`）：**内存计算单元行为模拟**，对照 double
  精准参考测真实误差（真实字节，3 种子取最差）。设备结构 = CIM crossbar：
  DAC 量化激活 → 模拟阵列组段累加（无逐元素舍入）→ ADC 量化组段部分和 →
  数字外围乘 E8M0 scale → fp32 跨组累加：
  - 位数扫描（信号归一 max|err|/RMS）：DAC6/ADC8 → 5.1e-2；DAC8/ADC10 →
    1.6e-2；DAC10/ADC12 → 4.0e-3；DAC12/ADC12 → 2.7e-3
  - 判决：**DAC 激活量化主导**（ADC 8→12bit 在 DAC=8 时几乎不动），
    要达到权重量化噪声量级（~1e-3 信号归一）需 **DAC≈10bit + ADC≈12bit**。
  - **理想模拟声明**：未建模器件噪声（cell 变异/IR drop/热噪声）→ 上表是
    理想无噪声**下界**，真实器件只会更差。
- **模拟污染教训（重要方法论）**：曾用"CPU 算法 + float 累加"冒充设备路径；
  更严重的错误是**把已删除的 C500 张量核规格（c500-kernel.md）当参照物复活**——
  C500 是污染源，已删除，不可再引用。设备路径必须按目标硬件的结构忠实建模：
  累加（CPU 8累加器树+double vs CIM 模拟组段+数字fp32）、量化点（CPU 无 vs
  CIM DAC/ADC）、scale 位置（CPU group 点积后 vs CIM ADC 后数字侧）全不同。
- 结论：内存计算单元的精度预算 = 由 DAC/ADC 位数决定，DAC≈10bit+ADC≈12bit
  才能到 ~1e-3 信号归一（= MXFP4 权重量化噪声量级）；但这是**算法层**预算，
  理想模拟未含器件噪声，真实设备需把器件裕量算进去（需硬件/cycle 仿真证）。
- 状态：硬件未到，黄金参考就位。内存计算单元 / RTL 第 4 课以它为准逐位对齐。

## 点2：算得快的同时，输出多级数据用于预取/预测 —— 现状与可行性

### 现状（"有没有人做过"）
- 分级置信度**概念**存在于硬件文献：TAGE/分支预测的 confidence、值预测、
  置信度数据预取器。这是老牌架构思想。
- MoE 专家预取**存在**：MoE-Infinity 的 locality 预取、若干 speculative-routing
  工作 —— 但多为"二元"（预测下一批 top-k，搬不搬），不是三档分级。
- 具体到"消费 softmax 尾巴 + margin 信号 + 衰减热表 → 三档（精确/预取/预测）"
  这个设计：**据我所知没有已落地的实现，是设计空间，不是已成品。**
  （待查文献核证：勿把"我知识盲区"当成"没有人做过"。）

### 可行性
- 软硬件都便宜：softmax 全分布本来就算出来了，消费尾巴零额外成本；
  RTL 侧 = 三个阈值比较器 + 三级优先队列 + 一张衰减表。
- **决定性变量是路由分布的 margin 结构**（第 k 名与第 k+1 名分数差）。
  margin 厚 → 分级信号可靠；margin 薄 → 预取尾巴就是白烧带宽。
- **K3 的 Quantile Balancing 正是 margin 杀手**：路由被训练成均匀，
  分数差被压缩 → 分级信号弱 + 历史热表也平（usage 均匀 → 无热集）。
  → 分级预取在"负载均衡激进"的模型（K3、DeepSeek aux-loss-free+bias）上弱，
    在"路由自然倾斜"的模型上强。这与"负载均衡杀缓存"论点同一根矛。

### 验证边界（重要）
- 现有 `expert_trace.bin` 只记录被选中的 (layer, expert) 对，**不含 softmax 概率**
  → 无法直接从现有数据测 margin 结构。
- 现有数据能测的切片：**每层历史频率分布**（top-k 稳定性 52.3%、
  衰减热表模拟）——这是当下唯一可实证的子问题。

### 实证切片：每层衰减热表（`tools/predict_hotset.py`）
方法：每个 run 开始时，用该层累计频率表（带衰减 γ）取 top-K 当预测集，
测 覆盖率 = |预测集 ∩ 本 run 专家集| / |本 run 专家集|（distinct 口径，warm）。
数据集：736 runs = 8 super-iter × 92 层，每层 distinct 专家 median=106、mean=108.8。

| predictor | K=10 | K=20 | K=30 | K=50 | K=80 | K=130 |
|---|---|---|---|---|---|---|
| γ=1.0/0.9/0.8/0.5（完全相同） | 11.4% | 22.9% | 34.3% | 57.2% | 84.5% | 92.3% |
| prev-run（上一轮同层全集，不裁剪） | 92.4% | 92.4% | 92.4% | 92.4% | 92.4% | 92.4% |
| prev-run-K（上一轮同层按频次裁剪 top-K） | 11.4% | 22.9% | 34.3% | 57.2% | 84.5% | 92.3% |
| oracle（上限） | 100% | … | … | … | … | 100% |
| random（地板） | 1.1% | 2.2% | 3.3% | 5.6% | 9.0% | 14.5% |

请求加权命中率（γ=0.8 热表，按请求条数计）：K=30 → 34.5%，K=130 → 99.9%。

**结论（对点2设计的直接判决）：**
1. **γ 完全无关**：γ=1.0 与 γ=0.5 顶层集合 0 次分歧 → 每层 top-K 在 8 个
   super-iter 间稳定。但注意这是"重头稳定"，不是"集合冻结"：
   同层相邻轮集合**逐位相同仅 0.3%**，Jaccard median=92.7%（min 81.4%），
   即每轮约 7% 的集合成员在漂移（漂的是低频尾巴，不是 top-K）。
2. **热表浅**：K=30（≈48.4GB）才 34.3%；要 92% 必须 K≈130（≈210GB）。
   每层 usage 近均匀（106~160 个 distinct，89 请求/run → 平均每专家 0.7 次，
   大部分专家每 run 只命中 1 次）→ 没有小热集，这正是 Quantile Balancing
   拍平路由的结果，与"负载均衡杀缓存"同一根矛。
3. **prev-run-K ≡ 累计表（数字逐位相同）**：上一轮同层的 top-K 就携带了全部信号，
   不需要累计表 → Tier-3 的历史表可以退化成"存每层上一轮的集合"。
4. **prev-run 全集 92.4% 是可用上限**（全层集合 ≈ 10,010 distinct ≈ 175GB）。
   注意 92.4% ≠ 精准答案：它是"仅用过去数据"的合法预测，0.3% 才逐位相同。
   "保持每层上一轮集合"是当前 trace 下唯一强的信号；但它是集合级的（无裁剪），
   一旦要裁剪就掉回 top-K 曲线（34%@48GB）。
5. **层间无信号**：同 super-iter 相邻层的集合 Jaccard median=4.8% →
   用上一层预测下一层是死路，只能做层内（同层跨轮）预测。
6. **口径提醒**：distinct 覆盖率 ≈ 请求加权命中率（小 K 差 <1%），K=130 时请求加权
   达 99.9%（被 top-130 覆盖的专家承载了几乎全部请求）。
7. **trace 代表性**：同层相邻轮 0.3% 逐位相同 → 输入并非完全重复，路由真实在变；
   但仍是单 workload、100k 请求，跨 workload 稳定性未验证。

**对设计的影响**：Tier-3 存在且便宜（退化成一表存上一轮集合），但被均匀性封顶——
在 ~48GB 档只能换 34%，要 92% 得 ~210GB。真正的救兵只剩 Tier-2（softmax margin），
而它**现在的 trace 测不了**（缺概率）。margin 若薄（Quantile Balancing 下很可能），
整个分级预取就靠"同层上一轮集合"这一根柱子。

### 关键交叉核对：case-k25（demo）与真实 K3 的路线分叉
仓库里 `case-k25/report.md`（demo 模型，60 层，每层 999 调用/357 unique，
60 行统计逐位相同 → 退化/玩具 trace）结论**相反**：
- 预算 4.51GiB：静态热表+LRU hit=0.4719，纯 LRU hit=0.1387 → **C/B=3.40x**，
  热表"值得做"。demo 路由高度偏斜（top20% 覆盖 0.86）。
- 真实 K3（`expert_trace.bin`，fixture README 明示 "a real model run"，
  92 层×896 专家，per-layer usage 近均匀）：同一方法只有 ~34%@48GB。

**这正是点2 的 skew/margin 轴在实证上的分叉**：
- demo 偏斜 → margin 厚 → 热表/分级预取有效（3.4x）
- 真实 K3 被 Quantile Balancing 拍平 → margin 薄 → 热表失效

**教训**：case-k25 的热表收益是"demo 偏斜路由"的产物，不能外推到真实 K3；
以它为据会给硬件立项。真实 trace 切片的价值 = 在立项前把这个外推证伪了。
反过来说，只要未来某次真实 run 的 margin 厚，Tier-2 立刻复活——目前只有
"带 softmax 概率的真实 trace"能判这条命案。

### 分层流式带宽需求（`tools/sim_stream.py`，2026-08-16）

**上游口径（kimi-k3-in-c 源码 gates.txt，实测）**：
- 每 token 专家权重 25.83GB = 92 层 × 16 top-k 专家 × 17,547,264 字节/专家
- **trunk（always-active 参数，56.7B 参 = 113.49GB bf16）每 token 全读、不可缓存**；
  上游实测单步 trunk 读 300.63GB（3 步累积 5b）
- 上游完整实测（228GB RAM + NVMe 流式 trunk）：0.015 tok/s 量级

**完整账本（trunk + 专家，专家按 prev-run 88.3% 请求加权命中）**：

| 速度 | trunk | 专家 miss | 合计 |
|---|---|---|---|
| 1 tok/s | 113.5 GB/s | 3.0 GB/s | 116.5 GB/s |
| 10 tok/s | 1.13 TB/s | 30 GB/s | **1.17 TB/s** |
| 30 tok/s | 3.40 TB/s | 91 GB/s | 3.50 TB/s |

**商品内存现实（有效带宽→可支持速度）**：

| 形态 | 带宽 | 支持速度 |
|---|---|---|
| DDR5 双通道 | ~102 GB/s | 0.9 tok/s |
| LPDDR5 手机 | ~51 GB/s | 0.44 tok/s |
| 服务器 8 通道 DDR5 | ~410 GB/s | 3.5 tok/s |
| HBM2e 单栈 | ~460 GB/s | 4.0 tok/s |

**专家侧缓存曲线**（每层留上一轮 top-K，只影响 25.83GB 专家段）：

| K/层 | 常驻 | 请求命中 | 专家 NVMe @10tok/s |
|---|---|---|---|
| 16 | 24 GB | 37.4% | 162 GB/s |
| 32 | 48 GB | 56.2% | 113 GB/s |
| 64 | 96 GB | 79.8% | 52 GB/s |
| 96 | 144 GB | 93.6% | 16.5 GB/s |

**判决（修正我此前的错误结论）**：
1. **我此前只算了专家、漏了 trunk，结论作废**。"96GB 常驻→93.6% 就地消化、
   商品 NVMe 就够"是**错**的——那只是专家 25.83GB 段，trunk 113.5GB/token
   才是大头且不可缓存。
2. **为什么"流式后"≈"无缓存"**：专家段只占全量 18.5%（25.83/139.3），任何
   专家缓存都只能在这 18.5% 里打转；trunk 是 always-active、无稀疏性，每 token
   100% 必读，缓存无法跳过。流式加载没失灵，是**瞄错了目标**（专家），而瓶颈
   在 trunk（上游实测 trunk 占 I/O 的 81%）。
3. 专家缓存有用但只救小头：把 25.83 压到 3.02 GB/token；trunk 113.5GB/token
   任何专家策略都动不了。
4. **完美运行（10 tok/s）需 ~1.17 TB/s 有效带宽 + 常驻 ≥139GB**（trunk 113.5
   + 专家缓存）。这是服务器 8 通道 DDR5 或 HBM 量级，**普通 PC/手机内存远不够**。
5. **内存计算的真正价值段落 = trunk 的 113.5GB/token**（always-active、
   不可缓存、必须从存储读进算力）。要消掉它只有两条路：trunk 近存
   （near-memory，权重住在算力旁）或压缩/结构化（KDA 复用已部分如此）。
6. **trace 局限**：prev-run 88.3% 命中来自**同一 workload 8 轮重放**；真实
   多用户不同 prompt 跨 workload 命中无此保证（predict_hotset.py 已注明未验证）。

### K3 vs Qwen3.6-A3B 计算对比（2026-08-18，估算，待 Qwen trace 校准）

**核心差异：激活参数口径。** K3 是"大而全读"（trunk 每 token 全量激活 56.7B），
Qwen-A3B 每 token 只碰 ~3B（Activated 3B）——算力差 23 倍、带宽差 ~90 倍。

| 项 | K3（实测/源码级） | Qwen3.6-35B-A3B（估算） |
|---|---|---|
| 总参数 | ~75B（trunk 56.7B + 专家） | ~35B（激活 ~3B） |
| 路由层 × 专家/层 | 92 × 896 | 48 × 64/128 |
| top-k | 16 | 4–8 |
| 每 token 激活参数 | trunk 56.7B 全读 + 专家 | ~3B |
| MAC/token | trunk 113.5 + 专家 25.8 ≈ 139 GFLOP | ≈ 6 GFLOP（3B×2） |
| 每 token 读字节（bf16/Q3） | 139GB（bf16） | ~1.3GB（Q3） |
| 10 t/s 需算力 | 1.39 TFLOP/s | 60 GFLOP/s |
| 10 t/s 需带宽 | 1.17 TB/s | 13 GB/s |

**概念澄清（量化只动带宽、不动算力）**：
- 算力 = 参与计算的**参数个数** × 激活比例 × 速度 → **与 Q3/Q4 无关**（乘加次数由
  参数量决定，不因存储 bit 数而变；且量化权重先反量化回 fp32 再算，计算精度一致）
- 带宽 = 参数个数 × **每个数几 bit** × 速度 → **与 Q3/Q4 强相关**（Q3 比 Q4 少搬 ~25%）
- 所以 `sim_compare` 里换量化只改带宽墙数字、不改算力墙——量化砸带宽墙不砸算力墙

**对项目的意义**：
- K3 那套"139G/token、10 t/s 要 1.17TB/s"的恐怖账，是**"接近 dense 的大模型"**的账；
  内存计算若服务 K3 必须吞 trunk 113.5GB/token 全量。
- Qwen-A3B 轻量（6 GFLOP、1.3GB/token），需求小两个量级——缓存/近存方案在 Qwen 上
  的门槛远低于 K3。开放项 A 的价值正是验证 K3 结论能否移植到这类轻量 MoE。

**跳变点的静态上下界（"能不能现在就算出 Qwen 的跳变"？答案：不能精准，只能锁区间）**：
- **跳变点 = 复用距离累积曲线的拐点 = 路由轨迹的函数**。轨迹 = 每个 token 选哪几个
  专家，是运行时行为（模型权重 + prompt 共同决定），**静态架构参数推不出唯一答案**。
  K3 的 138 槽 / 热集 median 106 也是 trace 实测的，不是算的。
- 但可静态锁定**跳变区间**：

  | 情景 | 命中率形状 | 跳变点 |
  |---|---|---|
  | 路由完全均匀（最坏） | 线性爬升、无尖峰 → 平滑型 | 接近专家池全量 |
  | 路由强幂律（最好） | 平台期长、到热集容量陡升 → 分簇型 | 很小（热集容量） |

  真实 Qwen 落两者之间——**这正是开放项 A 要实测定的东西**。
- **精准的必要前置**：需真实**张量形状**才能算每专家字节 / 每层槽数上限。
  电脑上 `llama-cli -m <qwen.gguf> --verbose 2>&1 | grep -i expert` 打印每层
  专家张量尺寸（静态量，可精确）；当前表内 Qwen 列均为估算。
- **唯一精准路径 = trace**：不用等 C 档全跑完，电脑跑一段推理 + `--moe-trace`
  钩子，收集几百 token 路由轨迹，离线即可画全容量-命中曲线、定跳变点。

> ⚠️ Qwen 列为估算：参数结构取自白皮书（L=48/E=64/128/K=4-8）公开口径，未用
> Qwen trace 实测校准。等 trace 出，替换为实测值。

### 上游实测内存阶梯（docs/PERFORMANCE.md）——"内存没到 256" 是伪命题

同机同 prompt 只加内存（cgroup 硬顶），输出 byte-identical：

| RAM | s/token | vs 8GB | GB read/token |
|---:|---:|---:|---:|
| 8 | 32.69 | 1.00× | 25.83 |
| 96 | 24.40 | 1.34× | 18.11 |
| 192 | 21.32 | 1.53× | 16.65 |
| 224 | 19.21 | 1.70× | 14.53 |

三件事：

1. **容量封顶 = 1.70×，且上游本就 228GB**。8→224GB 只换 1.7 倍；224GB 档
   实测 19.21 s/token = 0.052 tok/s，离 10 tok/s 还差 ~190×。"加内存"这条路
   上游已经走到头，不是缺的那条腿。
2. **224GB 档是算力墙，不是带宽墙**：该档每 token 只读 14.53GB，即使按
   ~200 GB/s（EPYC 7763 理论带宽，Milan 8 通道 DDR4）也只占 ~0.07s，而墙钟
   19.21s → **compute ≥ 99% of wall**。上游 C 引擎的 CPU 侧才是当前最硬闸。
3. **三层墙串联，10 tok/s 要三道闸同时过**：容量（≥139GB 常驻，加钱可解）
   → 带宽（~1.17 TB/s，HBM 可解）→ 算力（~2.6 TFLOP/s，AVX2 服务器 CPU
   不够，要多核 SIMD/GPU/加速器）。sim_stream.py 只量化了前两道（带宽），
   算力闸单靠内存数据推不出来，靠上游实测反推（阶梯 224GB 档 compute 99%、
   5b 的 I/O share 42% → compute 58%）。

**修正此前的错误结论**：上一轮我说"换 256GB 机器立刻 2-4 tok/s"是错的——
(a) 上游已有 228GB，容量线早已触顶 1.7×；(b) 2-4 tok/s 来自带宽假设，但
上游满内存实测被 compute 压在 0.052 tok/s。**带宽账本本身没错**（trunk
108.81 GB/token 实测确凿），错的是"带宽放开=速度上去"——还有算力这道闸。

### 路径排序：软件优先，CIM 收尾（2026-08-16）

**关键核算（同一台 EPYC 7763 上）**：
- 10 tok/s 需求 ~1.39 TFLOP/s = trunk 113.5 + 专家 25.8 GFLOP/token
- EPYC 7763 理论 fp32 峰值 ~1.3-2.5 TFLOP/s —— 够得着 10 tok/s 需求（边缘）
- 上游实测 19.21 s/token 只跑出 ~7.2 GFLOP/s ≈ 理论峰值 **0.3%**，也离本机
  GEMV 的 DDR4 带宽天花板（~1.4 tok/s）差 ~30×
- **"算力墙"的 99% 是 C 引擎自身低效**（分配开销/无预取/串行/fp32 重算），
  不是芯片算不动

**由此修正对"内存计算"的定位**：
1. **CIM 同时消两道闸**（修正我此前"只省能耗"的错误）：trunk 113.5GB/token
   搬运（带宽）+ ~113 GFLOP/token matmul（算力）都在阵列内就地完成。
2. 但 CIM 是**最终归宿，不是 10 tok/s 的前提**。前提是先让现有引擎跑到
   硬件天花板：0.05 → ~1.4 tok/s（DDR4 带宽顶）→ ~3 tok/s（8 通道 DDR5）→
   ~8-10 tok/s（HBM，此时卡算力）。CIM 在算力/能耗上都优于 HBM+CPU 方案，
   但对"先跑起来"来说成本高（113.5GB 阵列 + 精度契约 4e-3 vs 1e-3 +
   器件噪声未建模）。
3. **分层路径**：① 引擎重写（SIMD/多线程/预取/批处理）→ ② 大内存/HBM →
   ③ CIM 收尾。每级都在上一级到顶后才轮到。

### CIM 系统级量级估算（2026-08-16）

**换算基准**：10 tok/s = 1.39 TOPS（trunk 113.5 + 专家 25.8 GFLOP/token），
线性放大：100 tok/s ≈ 14 TOPS。

**算力不是 CIM 的墙，容量才是**：
- 模拟 SRAM CIM（按 DAC10/ADC12 精度契约打折）：5-50 TOPS → ~30-300 tok/s
- 数字 CIM（位串行/多周期）：100-1000 TOPS → ~700 到数千 tok/s
- 但 113.5GB 权重须全部常驻阵列：
  - SRAM CIM：单 die 阵列最多几十 MB 级 → 113.5GB 需天文数字芯片数/成本，
    现实不可行
  - DRAM 基近存/CIM：容量够（HBM 级），吞吐比 SRAM CIM 低 1-2 个数量级
    → 回到 ~10-50 tok/s 档
  - Flash/3D NAND 模拟 CIM：容量巨大、成本低，但读带宽和耐久性是硬约束
- **每 token 仍要电学读一遍 113.5GB**（CIM 只是"读出即算"）：100 tok/s →
  阵列读出率 ~11.4 TB/s，ADC 总吞吐/功耗爆炸。

**诚实结论**：10 tok/s 对 CIM 是低目标（算力上 30-300 tok/s 可达），但
介质成本 + DAC/ADC 精度/功耗把工程现实压回**几十~上百 tok/s**；再往上
host 侧（注意力 QK/PV、路由、softmax——CIM 不碰的部分）成新墙。量级是
"一个数量级左右"，不是两三个数量级。

### 流片导向模拟（2026-08-16）：器件噪声 + die 级吞吐

**① 器件噪声（`pim/sim_cim.c` 扩展）：加 cell 变异/列热噪声/IR drop 三样**
max|err|/RMS（DAC10/ADC12，3 种子最差，对照 double 精准参考）：

| 场景 | max|err|/RMS |
|---|---:|
| 理想（无噪声，原版复现） | 4.04e-3 |
| cell 变异 0.5% | 1.22e-2 |
| cell 变异 1% | 2.56e-2 |
| cell 变异 1% + 列噪声 0.1%FS | 3.49e-2 |
| cell 变异 2% + 列噪声 0.1%FS | 5.50e-2 |
| cell 变异 2% + 列噪声 0.3%FS | 9.09e-2 |

- **位数加不回去**：cell 变异 1% 时 DAC12/ADC12 也到不了 2.5e-2 以下——
  器件噪声主导，提高 DAC/ADC 位数无效。理想档逐位复现（4.04e-3）证明
  噪声注入本身没污染理想路径。
- 流片含义：保住 ~1e-3 契约需 cell 变异 <0.1%，对模拟 cell（NAND 常见
  >0.5%）极苛刻 → **只有 SRAM/DRAM 数字 cell 能满足精度契约**。

**② die 级吞吐（`tools/sim_cim_throughput.py`）：三道闸串联**
- 账本：trunk 56.7B 参 = bf16 105.6GB / MXFP4 28.0GB；每 token 1.95G 次
  ADC 转换（trunk 1.77G + 专家 miss 0.18G，group=32）
- 容量闸（需 die 数 = (trunk+96GB 缓存)/介质密度）：SRAM 模拟cell 0.2GB/die
  → bf16 806 颗 / MXFP4 496 颗（荒谬）；DRAM 近存 16GB/die → 13/8 颗；
  NAND 模拟 128GB/die → 2/1 颗
- ADC 吞吐闸（SAR 转换≈bits×1ns，1024 列/die）：8bit 128 Gconv/s、10bit
  102 Gconv/s、12bit 85 Gconv/s → 单 die 44-66 tok/s
- host 闸：非 matmul 40 GFLOP/token @10tok/s = 0.4 TFLOP/s（CPU 给得起）

**判决**：
1. **ADC 吞吐不是闸**——1 颗 die 就锁 40-50 tok/s，容量才是第一墙。
2. **SRAM 模拟 cell 装不下 trunk**（~800/500 颗），只配专家侧/小模型。
3. **NAND 模拟 1-2 颗 die 容量够、吞吐够，但精度过不了关**（cell 变异
   >0.5% → 1.2e-2 起，与"10bit 吞吐优势"正好抵消）。
4. **唯一的自洽路线 = DRAM 近存 + 数字 cell + MXFP4 trunk**：8 颗 die
   容量够、数字 cell 精度可保 ~1e-3、~50 tok/s 吞吐。这正是"trunk 近存"
   结论在流片约束下的具体化。
5. 未建模（只低不高）：模拟累加 settle 时间、DAC 驱动、跨 die 部分和聚合。

## 开放项 A 真机闭环（2026-08-18，Qwen3.6-35B-A3B Q3_K_S，40 层，CPU-only `-ngl 0`）

**采集链路**：SparkMoE fork（c77dd68，sparse-checkout 本地编译）自写最小 CLI `research-cli`
+ C++ trace 钩子（`llama_moe_set_trace_file` → remap 前 dump JSONL）；两条独立真实 trace
（115/121 token）落盘 `data/traces/trace-{1,2}.jsonl`，分析在 `data/analysis/`。

**复用距离形状 = 幂律热尾（平滑，非 K3 双簇）**：每层 256 专家，n50 平均 15-20，
top20% 覆盖 0.50-0.74，熵 5.2-7.4 bits（均匀 = 8）。

**容量-命中曲线平滑爬升（无 36% 平台）**：静态银行 uniform/全局贪心
4GiB→0.935/0.945、8GiB→0.997/1.0、12GiB→1.0/1.0（专家权重总量 ~12.9GB，12GiB 全驻留）。
→ **中间档位有用，无需全模型驻留**——"少量组 + 共享聚合层"方案在 Qwen 上成立。
与 K3 双簇不冲突（K3 那是对作者钉死请求顺序的假象，见 README 复盘）。

**cache-vs-trunk 分配**：uniform 每层静态 ≈ global 贪心（4GiB 差仅 0.01），均匀分配即够；
同预算动态 LRU 仅 0.83（静态热表 +0.11pt 命中）。

**跳变点精准定位（整数槽扫描 1-32 槽/层，`slot_sweep`）**：
- LRU 拐点 = **8 槽/层（= 404MB）**，Δ 最大 +0.175/+0.150，两条 trace 一致；
  陡增区完整区间 **6→9 槽/层 = 0.282→0.423GiB**（6 槽前仅 0.2%-4% 命中，8 槽跳至 0.29）。
- 8 槽 = 越过每层核心热尾下沿（n50=15-20），LRU 第一次能留住批内高频专家。
- 9 槽后增益骤降为 +0.026→+0.01/槽 的平缓递减，**无平台**（与 K3 三堆分布的平台型根本不同）。
- 真机交叉验证闭合：512MiB=10 槽/层 命中 0.3706 ≈ 离线 0.3875，落在拐点右侧。

**B 档真机验证（同日同模型同 prompt，`data/bscan/`）**：`--moe-cache-mib`
4/8/12/16 GiB 实测命中 **0.782 / 0.839 / 0.850 / 0.845**（平滑爬升，与离线 LRU 预估一致）；
驱逐数 4287 / 105 / 0 / 0。miss 分解 = compulsory（每专家首次，40 层 × unique≈120 ≈ 4800，
恒在）+ 驱逐重装（4G: 2866 → 12G: 236）——12GiB 已逼近纯 compulsory 下界；16GiB 无驱逐
但命中略降属噪声。

**LRU 到不了 90% 是 compulsory 地板（短 trace 口径），非容量**：trace-1 仅 121 token，
每层 unique≈120/256，专家首触必 miss ≈ 40 层×120 ≈ 4800 次，占 touches（~35000）的
**13.7%** 为命中率物理下限。12GiB=243 槽/层已装下全部出现过的专家（驱逐 236），实测 0.850
已贴死 1−4800/35000≈**0.863 容量上限**。

**✅ 长 trace 稀释复核（`data/traces/trace-3.jsonl`，240 token）**：
- **compulsory 地板由 13.7% 稀释到 8.5%**：每层 unique 均值 ≈162.7（240 token 下
  unique 亚线性涨），40 层首触 miss ≈ 6508 / touches 76800 = **8.5%** → 理论 LRU 上限
  ≈ **91.5%**。
- **纯 LRU @8GiB 实测仿真 = 0.9086（90.86%）**，与理论上限 91.5% 吻合——**长 trace 下
  纯 LRU 能到 90%**，彻底坐实"0.85 是短 trace 测量口径而非容量上限"。8GiB 已够 Qwen
  专家全停留（static 4GiB→0.898、8GiB→0.997、12GiB→1.0）。
- **同步修正决策门**：长 trace 下 4GiB 预算 C/B = 1.08x、D/B = 1.09x（trace-1/2 短 trace
  是 1.14-1.15x）——**≤4GiB 预算下 C / B < 1.10 决策门不再通过**，静态热表收益
  被长 trace 摊薄。8GiB 档 C=0.9125 vs B=0.8430（+7pt）仍有利，属预算充足档。
- 教训：短 trace 下决策门偏乐观，长 trace 才接近真实部署形态（touches 涨、unique 亚线性）。

**决策门与档位**：离线 C/B = **1.14x / 1.15x**（两条 trace 一致，≥1.10 → 静态热表值得做 C++）；
D 档（热表+时序）≈ C 档（+0.002），时序局部性仅 0.35-0.39（一步预取上界），静态热表已吃大头。

**C 档真机端到端（4GiB 预算，cap63 热表 = pin 63 专家/层 + LRU 18 槽/层，`data/cscan/`）**：

| 测试负载 | 热表来源 | miss | vs 无 pin |
|---|---|---|---|
| trace-1 | 无 pin（B 档） | 7666 | — |
| trace-1 | trace-1（同分布） | 6304 | **−17.8%** |
| trace-1 | trace-2（交叉） | 6504 | −15.2% |
| trace-2 | 无 pin（B 档） | 6390 | — |
| trace-2 | trace-1（交叉） | 7049 | **+10.3% 反亏** |

- 同分布 pin = 最佳（−17.8% miss），方向支持离线 C/B 预估。
- **跨 trace 泛化不对称**：trace-1 偏斜更强（n50 更小、top20% 覆盖更高）→ pin 有效；
  trace-2 负载更均匀 → pin 专家命中低且挤占 LRU 槽（81→18）→ 净亏。
- **生产启用条件**：热表须采自与部署负载同分布的长 trace（115-121 token 短 trace 不足
  以稳定泛化）；pin 预算必须留足 LRU 动态空间（pin 63 + LRU 18 已是极限）。
- 实现发现：pin 专家总数 > 缓存槽数时驱逐路径抛 "no evictable MoE expert slot"
  （moe-cache.cpp:82/150）；4GiB 下 85 pin/层必崩，cap ≤63/层正常。

**对方案的意义**：Qwen 平滑热尾 → 中间档位缓存即有效（不同于 K3 双簇只两态）；
但**本机仍变现不了**（sim_compare 判定算力墙主导，芯片纯缓存增量=0）——缓存路线在
Qwen 上成立（机制层），变现仍需 CIM/卸载专家 GEMM。

### ✅ 真机闭环后的战略推演（2026-08-19，基于 trace-1/2/3 + B/C 档真机，可被后续推翻）

**推演一：静态热表（pin）在 Qwen 上应降级甚至放弃。** 证据三重叠加：
C/B 长 trace 掉到 1.08（<1.10 门槛）→ 真机跨 trace 反亏 +10.3% → 纯 LRU 8GiB 已
90.86%（距理论上限 91.5% 仅差 0.6pt，pin 的增量不存在了）。pin 收益只在"热表与负载
同分布"时成立（trace-1 偏斜强时 −17.8%），而生产负载分布会漂移 → 长期必然反亏。
**推论：软件栈砍掉 C 档 C++ 热表实现与 pinned 接线，保留 B 档 LRU + 容量档位**
（白皮书 §4 行动 3 前提失效）。

**推演二：强制性下界一锤定音——专家全驻留只需 16GB。** compulsory 8.5% + 专家全量
~12.9GB → 16GB 内存即全驻留，miss 之后 100% 是首次冷启动。分叉：
- "把专家塞进近存"的存量竞争在 Qwen 上没有意义（一次加载永久驻留，无需内存计算）；
- 内存计算若服务 Qwen，目标必须转向 **trunk 和算力**，而非专家篇。

**推演三：Qwen 不构成内存计算刚需——赛道判断修正。** K3 vs Qwen 的反比：
| 项 | K3 | Qwen-A3B |
|---|---|---|
| 算力需求@10t/s | 1.39 TFLOP/s | 60 GFLOP/s（CPU 峰值 3% 就够） |
| 带宽需求@10t/s | 1.17 TB/s | 13 GB/s |
| 专家全驻留 | 175GB（服务器/HBM 级） | 16GB（普通 PC） |

Qwen 类轻量 MoE 实测 5.58 t/s 不是硬件不够，是**引擎低效（0.3% 利用率）**——
它天生轻，需求端不存在"内存计算"。K3 那种"大而全读"才是刚需场景，却又是缓存死局
（层内聚拢/全驻留只有一条路）。**战略张力：内存计算服务的恰是缓存最难啃的 K3，
缓存好啃的 Qwen 又不需要内存计算——这是稀疏 vs 全读架构的一组反比，非巧合。**

**推演四：出路收敛——目标 Qwen，硬件重心 = 卸载 Sparse/专家 GEMM。**
1. 目标模型 = Qwen，但重心从"缓存命中"移到"**算力卸载进内存侧**"（CIM GEMV），
   带宽墙自动破 24-29 t/s（sim_compare 已推）。
2. 每 token trunk 2.2-2.5B + 专家活跃 ~320 专家/层 × 1.26MB；算力卸载后
   compulsory 8.5% 成为"CIM 也要处理首次"的一次性成本（全驻留后消失），非长期瓶颈。
3. 同时放弃静态热表、放弃大容量专家竞争 → 软件复杂度骤降，预算全给算力卸载。

**一句话**：真机闭环没有回答"该怎么做"，但**把不该做的（静态热表、专家近存）全部
证伪了**，留下唯一站得住的答案——**在 Qwen 上，内存计算的价值不在内存，在它自带的
算力。**（标注：以上为推演，后续可用 RTL/ CIM 仿真或更大模型 trace 破）

**待办（可选）**：① ✅ 长 trace 稀释复核（trace-3，240 token → compulsory 13.7%→8.5%，
LRU @8GiB=90.86%，并发现 ≥300 token 长 trace 下 4GiB C/B 掉到 1.08x）；
② pin/LRU 分配比扫描（40/41 vs 63/18 vs 0/81）定最优分账；③ trace-1-fine（hot_list
顶 42 专家/层）与 fine2 两套热表口径核对。

## Q3 GEMV 引擎基准（2026-08-18）

> **关键发现：模型实际格式为 Q3 (3-bit)，非之前测试的 MXFP4 (E2M1, 4-bit)。
> Q3 天然更快：查表 8 项 vs 16 项、提取 `&0x07` 单指令、值域均匀整数 {-4..3}。**

### Q3 格式说明
- 3-bit 权重，8 个值 {-4, -3, -2, -1, 0, 1, 2, 3}
- 简化打包：每 weight 1 byte 低3位，group=32
- benchmark 用简化 scale (1 byte/group → float)

### Q3 全变体对比 (cols=3584, reps=100)

| 变体 | 64行 (1 expert) | 512行 (8 experts) | 20480行 (320 experts) |
|---|---|---|---|
| A scalar(d) | 678 MB/s (1.4 GFLOP/s) | 683 (1.4) | 767 (1.5) |
| B opt(f32) | 1353 (2.7) x2.0 | 1354 (2.7) x2.0 | 1421 (2.8) x1.9 |
| C v2(unpk) | 1003 (2.0) x1.5 | 1000 (2.0) x1.5 | 1354 (2.7) x1.8 |
| D v3(flat) | 1374 (2.7) x2.0 | 1365 (2.7) x2.0 | 1142 (2.3) x1.5 |
| **E v4(neon)** | **1376 (2.8) x2.0** | **1921 (3.8) x2.8** | **1671 (3.3) x2.2** |
| F v8(4row) | 716 (1.4) x1.1 | 926 (1.9) x1.4 | 622 (1.2) x0.8 |
| **G v9(2pass)** | **1197 (2.4) x1.8** | **1987 (4.0) x2.9** | **1325 (2.6) x1.7** |
| opt x8t | — | 1354 (2.7) x2.0 | **3443 (6.9) x4.5** |
| v8 x8t | — | 948 (1.9) x1.4 | 1828 (3.7) x2.4 |

### 关键结论

1. **Q3 比 MXFP4 快 50-80%**：v4 NEON Q3=1921 MB/s vs MXFP4 v8=1101 MB/s (512行)
   - 原因：查表 8→16 项 (L1 完全驻留)、提取 `&0x07` 单指令、值域均匀整数

2. **v8 (4-row) 在 Q3 下反而最慢**：Q3 查表太小不需要多行隐藏延迟，4行指针+累加器
   占太多 NEON 寄存器导致溢出。v8 的"多行共享x"优势在 Q3 格式下被寄存器压力抵消。

3. **v9 (2pass) 在 Q3 下表现良好**：512行 1987 MB/s (4.0 GFLOP/s)，因为 Q3 的
   dequant 更简单（无浮点 scale 乘法），2-pass 架构的额外 buffer 开销被简化。

4. **8线程 opt x8t = 3443 MB/s = DRAM 的 50%**：Q3 格式下多线程扩展性好。

5. **vdotq_s32 (int8 dot product) 失败**：x→int8 量化开销（求absmax + scale + 转换）
   远超 vdotq_s32 本身的加速，比 scalar 还慢 5x。

### MXFP4 vs Q3 性能对比 (512行/8 experts, 单核)

| 格式 | 最优内核 | MB/s | GFLOP/s |
|---|---|---|---|
| MXFP4 E2M1 (4-bit) | v8 (4-row) | 1101 | 4.4 |
| Q3 (3-bit) | v4 (NEON) | 1921 | 3.8 |
| Q3 (3-bit) | v9 (2pass) | 1987 | 4.0 |

> 注：Q3 GFLOP/s 略低于 MXFP4 是因为 Q3 每元素只做1次 int→float 转换 + 1次 FMA，
> 而 MXFP4 做2次 nibble 提取 + 2次 FMA。但 Q3 的 MB/s 更高因为数据量更小(3-bit vs 4-bit)。
