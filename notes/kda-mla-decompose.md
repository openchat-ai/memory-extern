# KDA / MLA 拆解：它们是不可约的稠密墙，还是有重构空间？

> 2026-08-27 · 接续 MoE「先路由后搬运」实锤（见 independent-stack §14.2）
> 目标：判断 KDA 与 Gated MLA 两类注意力层能否复制 MoE 的「先算小权重、后精准搬运」模式
>
> **⚖️ 总裁决（2026-08-29）**：真 K3 张量分解实测（见 §19）判死 qkv/trunk 满秩墙——张量分解对 h_in 无收益，量化路线也已整体关闭（trunk 保 fp16，见 independent-stack B.9-B.12 与 k3-verdict §八）。本文 §1-§18 的"可压/分解"探索为历史记录，仅存档，不再作为行动方向。

## 一、与 MoE 的本质差异

MoE 能拆，根源是**存在「小权重决定大权重取舍」的结构**：
- router（gate）= 7168×896 ≈ 6.4M 参数，常驻
- 它决定 896 个专家里读哪 16 个

**注意力层的致命不同：没有这种「取舍」结构。**
attention 的每个输入 token 都要用全部 Q/K/V/O 矩阵，没有「先选一部分」的余地。
→ KDA/MLA 在「搬运取舍」层面，是**不可约的稠密墙**。

## 二、但「不可约」不等于「不可压」——三张牌

### 牌 1：权重按 token 均匀使用 → 但可优化读取路径
- KDA/MLA 权重每 token 每层全用，无法稀疏读
- 但其投影矩阵是**行列固定的 GEMM**，读取可以：
  - 按 `b` 维度并行分片（batch 共享，只读一次）
  - 权重与激活复用（同一批 token 共享同一份权重，读一次算多次）
- **这是「共享」而非「取舍」** —— 不省单 token 流量，但省跨 token 流量

### 牌 2：KDA 循环状态小 → 可常驻 SRAM（前面 KDA 系列已讲）
- 循环状态 = O(d×d)，与序列长度无关，几 MB 级
- 但 **KDA 的权重（g_proj 门控投影等）仍然是稠密的，每 token 全读**

### 牌 3：量化 / 低精度（前面 QAT/MXFP4 已讲）
- 权重已 MXFP4，2.12 bit/weight
- 已把注意力层权重的「单位读取成本」压到最低
- 这是唯一的「搬运量」压缩手段，且已用尽

## 三、结论：KDA/MLA 是物理稠密墙，重构空间在「层外」不在「层内」

层内的 Q/K/V/O 投影，是每个 token 绕不过的稠密矩阵乘法。
**不能像 MoE 那样靠 router 取舍**，只能：
1. 用 batch 共享摊薄（改变不了单 token，改变整体吞吐）
2. 用 MXFP4 压单位成本（已用尽）
3. **层外思路**：KDA 循环状态常驻 + AttnRes 仅 8 层摘要 → 注意力本身的「存储」可省
   但注意力「权重」仍是稠密墙

## 三·五、latent MoE 的精确结构（重要更正，防记错账）

K3 是 **Stable LatentMoE**（sglang/waste 源码实锤）：
```
routed_expert_down_proj: 7168 → 3584   ← 稠密，所有专家共享
专家(896): 3584 → 3072 ×2，运行在 latent 空间  ← 唯一可按路由取舍的部分
routed_expert_up_proj: 3584 → 7168    ← 稠密，所有专家共享
RMSNorm before up_proj
```

**关键：down_proj / up_proj 是全体专家共享的稠密矩阵，每 token 全用。**
→ 它们属于「trunk 稠密墙」，已计入 trunk 36GB。
→ 「先路由后搬运」能省的**只有中间那 896 个专家**的读取，
  省幅 = 专家侧流量 × (880/896)，而不是省掉整层。
→ 专家 25.83GB 中按路由省读的，是「专家本体」（down/up 之外的中间段）。

## 四、对「捅破结构」的最终判断

- **MoE 专家：可捅破**（先路由后搬运，省 880/896）
- **KDA/MLA 注意力权重：不可捅破**（稠密墙，靠 batch 共享 + 已用尽的量化）
- **注意力状态：可省**（KDA 循环状态常驻，AttnRes 摘要 56KB）

→ 真正值得捅破的仍是 MoE 的「先路由后搬运」；注意力层是物理天花板。

## 五、数量化（待 T8 实测）

- 每 token 总流量 = 专家 25.83GB + trunk 36GB（量化后）
- 若「先路由后搬运」成立：专家侧能省的比例 = (880/896) × 命中精准度
- 理论省幅：专家流量最多降到 ~0.46GB（只读 16 专家的下界）→ 但受缓存/预取现实约束

## 六、提取 router 的实际读写依赖（本轮核心）

> ⚠️ 本章的"替身/蒸馏架走 h_in"探索已被 8-29 总裁决收敛：压缩/蒸馏路线整体关闭（§19 qkv 满秩墙 + 用户定案）。§6.8 的 L3 统计替身实测（32.1%）保留为参考数据，但 L1/L2 激活替身不再投入。

> 目标：把「算一个 token 的路由」钉死到「它到底碰了哪些权重张量、哪些 slice」，
> 精确回答：要拿到 top16，哪部分权重是绕不开的稠密墙，哪部分可以只读一片。

### 6.1 router 权重本身（极小，可完全常驻）

源码实锤（sglang `kimi_linear.py` / `kimi_k3.py`）：
```
gate = ReplicatedLinear(hidden_size=7168, num_experts=896, bias=False)
router_logits, _ = self.gate(hidden_states)
```
- **gate.weight：7168 × 896 ≈ 6.4M 参数**，无 bias
- 预测后处理仅：`e_score_correction_bias`(896 标量, selection only) + sigmoid + top16
- **→ gate.weight + correction_bias 是 router 的「所有权重」，
  合起来几十 MB，完全可以常驻内存，无需搬运**
- **这意味着：算路由本身，不需要任何专家权重，不需要任何 KDA/MLA 的 Q/K/V/O 权重。**

### 6.2 router 的输入依赖链（真正的墙在这）

```
router_logits = gate.weight ⊗ h_in
   h_in = post_attention_layernorm(attn_out)      # 入层向量
      attn_out = self_attn(KDA 或 Gated MLA)       # 本层注意力输出
         # 注意力 = Q/K/V/O 投影，全稠密，每 token 全读
      h_in（进层）出自 input_layernorm(h 前层)
```

**核心矛盾：**
- router 的**权重**（gate.weight）极小、可常驻、可独立提取 ✅
- 但 router 的**输入** h_in 依赖「本层完整注意力输出」，而注意力依赖本层 KDA/MLA 的稠密权重

→ **「提取 router 读写的依赖」的精确答案是：**
   router 真正独用的权重 = gate.weight + correction_bias（可常驻）；
   但 router 要工作，还需要「本层注意力的输出」h_in —— 这需要先读并算完本层 KDA/MLA 稠密权重。

### 6.3 有没有可能只提取「产生 h_in 的最小子集」？

两条路（都诚实标注代价）：

**路 A · 本层注意力算完才路由（现状，100% 精确）**
- 必须读：本层全部 Q/K/V/O（稠密）+ gate.weight
- 代价：注意力权重是绕不开的稠密墙
- 收益：路由精确，top16 精准

**路 B · 轻量化路由（跳过部分注意力）**
- 用更早的 h（如进层 h、或上一层的 h）直接喂 router，或用一个轻投影近似 h_in
- 不读/少读本层注意力权重 → 但路由是**近似**，top16 命中率 < 100%
- 这是「用 h 层预测 + routing-driven prefetch」的老路（前面 35.3% 命中实测）

**路 C · 精确提取 gate.weight 单独常驻 → 但喂它完整/近似 h_in**
- gate.weight 一定常驻（省掉它的搬运）
- h_in 要么走 A（精确，稠密墙），要么走 B（近似，省注意力权重读取）

### 6.4 结论

- **能被「提取」的 router 依赖 = gate.weight + correction_bias** —— 极小，常驻，这部分搬运直接归零
- **不能被提取的 = 本层注意力输出 h_in 的产生** —— 依赖 KDA/MLA 稠密权重，是物理墙
- **所以「先路由后搬运」的精确实义：**
  router（gate.weight 常驻）在**当前层注意力算完后瞬间**拿到 h_in → 立刻算出 top16 → **后续只精准搬运/download 这 16 个专家本体**（省掉 880/896 的专家读取）
- 唯一绕不开的稠密部分 = **注意力 Q/K/V/O 权重**（属于 trunk 36GB，本来就不按路由取舍）

→ **每 token 真正能被「先路由后搬运」省掉的，是专家本体 25.83GB 里的 (880/896)；注意力稠密墙（trunk 36GB 中）不变。**
→ 这是本轮拆解的最终、可量化结论。

### 6.5 h_in 的双用途 —— 决定「解耦」边界的钥匙（2026-08-28）

**直接回答「attn_out / h_in 除了算 route 还有别的用途吗」：有，而且是最关键的一个。**

sglang `kimi_k3.py` 实锤（§14.2）：
```
router_logits, _    = self.gate(hidden_states)      # 用途① 喂 router → top16
final_hidden_states = self.experts(hidden_states, topk_output)  # 用途② 喂 experts
```
**gate 和 experts 吃的是同一个 hidden_states（= h_in）。**

| 用途 | 喂给谁 | 作用 | 可被简单算法取代？ |
|---|---|---|---|
| ① | router (gate) | 算 top16 选专家 | **可以**（用进层 h / 上一层 h 近似，命中率为代价） |
| ② | experts（MoE 本体） | 被选 16 个专家的**真实前向输入** | **不行**——这是真正的计算，不是 overhead |

**关键含义（信源分开）：**
- h_in 作为 **experts 前向输入**（用途②）：不可替代 —— 替换会污染专家计算结果
- h_in 作为 **route 选择依据**（用途①）：可以用更早的 h（进层输入 / 上一层注意力输出）
  **近似替代** —— 预测只影响"提前搬运哪个专家"，**不影响最终计算的正确性**

→ **这恰恰支持路 B（轻量路由）：预测 route 的命中率损失只影响搬运/预取，
不会让型号算错 —— 是"搬得快 vs 搬得准"的权衡，不是正确性取舍。**

### 6.6 下一斧：h_in 到底存的是什么？能否用简单算法取代？（2026-08-28）

不急说"没辙"。先问：**h_in 这个 7168 维向量，相对进层输入 h 前，到底多了什么？**

- h_in = post_attention_layernorm(attn_out)
- attn_out = self_attn( input_layernorm(h 前) )  ← 注意力（KDA/MLA）对进层输入的变换
- **h_in 相对 h 前的变化量，就是"本层注意力贡献"**

**可检验假设（下一步用真实数据验证，不靠猜）：**
- h1 若 **h_in ≈ h 前**（注意力输出与原输入高度相关/残差主导）→
  route 主要由**进层输入**决定 → 可用简单算法（进层 h 甚至线性投影）取代，命中率高
- h2 若 **h_in 与 h 前差异大、且集中在少数维度** → route 由注意力带来的少数特征主导 →
  用低维/稀疏近似，而非完整注意力
- h3 若 **h_in 与 h 前基本正交** → 无法简单取代，得走 KDA 的某种廉价近似

**验证手段（需要真实激活量，非 shape）**：拿 kimi-k3-in-c（或 CPU runner）在真实权重上
对若干 token 导出 (h 前, h_in) 对，算 相似度 / 余弦 / 低秩拟合误差。
→ 目前机器无权重源，此项标记为**待真实数据**。

### 6.7 蒸馏「小小替身」取代 h_in 的 route 用途（2026-08-28）

**思路**：不能完整算出 h_in？那就**蒸馏一个小网络「替身」近似它 / 近似它的 route 结果**，
不必等完整注意力。替身取代的是 h_in 的**用途①（选专家）**，不碰用途②（专家前向输入）。

**替身的三个层次（从易到难）与各自训练数据缺口：**

| 层次 | 替身学什么 | teacher | 训练特征 | 数据缺口 |
|---|---|---|---|---|
| L1 | h 前 → top16（直接出选专家） | 真实 router(gate⊗h_in→top16) | 需要 h 前/输入向量 | **需激活量** |
| L2 | h 前 → h_in（近似注意输出） | 真实 KDA/MLA 的 h_in | 需要 (h 前,h_in) 对 | **需激活量** |
| L3 | 纯统计/层内偏好 → top16 | 真实路由轨迹 (layer,expert) | 只需历史轨迹 | **本机已有 ✅** |

**关键卡点：L1/L2 都需要真实激活向量做训练特征；L3 不需要。**

**L3 变体（本机立刻可做，无需权重源）：**
现有真实轨迹：90% 重复、触及池子仅 12.1%、ρ=0.279 强 Zipf。
→ 「层内专家偏好」(per-layer expert popularity) 本身就是可蒸馏的小替身：
  - 每层一个专家频率分布（92×896 个标量，≈82K 参）
  - 规则路由：每层取频率 top16 → 可当 baseline 与「真实 top16」比对命中
- **这是先用已有数据试水，能立刻量化「统计替身」的天花板**

**L1/L2（真正的"小小替身"，需激活量）：**
- 若拿到 (h 前, h_in) 对：可用一个小 MLP/低秩投影学「h 前 → h_in」，
  student ≈ 若干 MB（远小于 KDA/MLA 的 60GB），专用于喂 gate 选专家
- 命中率若够高 → 注意力稠密墙(trunk)可被替身"架走"，这是本条思路的终极价值
- 命中率若不够 → 退回 L3 统计兜底

**结论**：替身方向可行且已分好层。L3 用现有轨迹即可动手；L1/L2 需要数据环境。
先做 L3 量化「统计替身」下限，同时找机会拿激活数据冲 L2。

### 6.8 L3 实测：统计替身真实命中率（T11, 2026-08-28）

用现有真实轨迹做「层内频率替身」评估（`tools/distill_route_proxy.py`）：

**⚠️ 重要教训 — 第一版评估口径坏了 (假 100%)：**
- 我先按"前/后半切分 train/test"，得替身A 命中 100% —— **那是假象**
- 因为轨迹结构是「每层独立批」(先采 layer1 多条，再 layer2...)，非 token→92 层链条；
  前/后半切分导致 train/test 覆盖同一层，测的是"该层专家集合稳定"，非"预测下一个"
- **修正为逐层「时序留一」**：用该层前 k-1 条历史预测第 k 条的选中专家

**修正后真实结果：**
```
[时序替身: 每层历史 top16]   命中率 = 32.1%
[对照: 随机(match pool)]     ~1.8%
[参考: LRU 缓存 1GB]         ~35.4%
[参考: 预测线 ρ=0.279]       35.3%
每层平均唯一专家 = 108.8  (共 896 个全局专家)
```

**解读：**
- **32.1%** = 零激活向量的纯频率替身，已逼近 LRU(35.4%)/预测线(35.3%)，
  远超市随机(1.8%) → 统计替身方向有真实地基 ✅
- 每层平均唯一专家 108.8 → K3 层内路由活跃，单一频率 top16 只能抓最热 16 个(~32%)
- **终极价值未兑现**：纯频率没用「进层激活特征」。若 L1/L2 用 h 前喂替身，
  命中或超纯统计 → 那才是「架走注意力稠密墙」的正主（需激活数据）
- **教训**：评估口径必须时序留一，前/后切分在"每层独立批"轨迹下测的是集合稳定性假象

## 九、T12 源码实锤（拉回 kimi_k3.py + attn_residual.py）

> 之前 §6 是二手结论（websearch）。本轮把 sglang `python/sglang/srt/models/kimi_k3.py`
> 与 `sglang/srt/layers/attn_residual.py` 原码拖回逐一核对。

### 9.1 router 输入的真实公式（含 "h_in 存的是什么" 的答案）

K3 层 forward（标准残差路径，`kimi_k3.py:2458-2467`）：
```
hidden_states = input_layernorm(h, residual)
hidden_states = _run_self_attn(...)                    # 完整注意力
hidden_states = post_attention_layernorm(attn_out, residual)
re = self.mlp(hidden_states)   # → 内部 self.gate(hidden_states) 算 router
```

AttnRes 层 forward（`kimi_k3.py:2588` → `attn_residual.py:339 aggregate_stream`）：
```python
rows = [bank[0..nvb-1], prefix_sum]     # [T, nvb+1, H]: 之前 block 摘要 + 当前 prefix
normed = score_norm(rows)               # RMSNorm 每行
scores = score_proj(normed)[0]          # rank-1 [H→1] 每块一个标量分数
probs  = softmax(scores)                # 8 个块(摘要)的注意力权重
h_in   = Σ_probs * rows                 # = 跨全部历史 block 的 softmax 混合
```

**"h_in 存的是什么" 的源码级答案：**
- **不是单个向量**，而是 **「跨全部前驱 block 摘要的 softmax 加权混合」**
- 每行 = 一个 **block 级 summary**（该 block 输出的 7168 维残差，整块只存 1 个代表向量）
- 混合权重来自 rank-1 `score_proj`（7168→1）+ softmax —— 本质是一个**几十维的小注意力**
- AttnRes 总状态 ≈ 8 块 × 56KB（`~288MB` over 93 层按块存）—— 这就是 K3 跨层信息流

### 9.2 这如何改变了「能否简单取代」的判断

- **h_in 本身的计算极轻**：~9 行 × 7168-d，rank-1 打分 + softmax + 加权和，
  没有大矩阵 —— 这**不是**「算 h_in 贵」
- **真正贵的是「产生 block summary」**：每个 block 的 summary 是**该 block 3×KDA+1×MLA
  完整跑完的输出残差** —— 要得到 summary，必须先完整算注意力（QKV/O 稠密墙）
- **结论**：想「绕开注意力直接算 h_in」，等价于想「不跑 KDA/MLA 就得 block summary」——
  但 summary 正是注意力的产物。**这是闭环：h_in 依赖 summary，summary 依赖注意力。**

### 9.3 对蒸馏替身方向的终审（结合源码）

- **替身能替代的**：h_in 的**用途①（选专家 top16）**——可用进层/layer-N 的 summary 预测，
  只影响搬运/预取，不影响正确性（§6.5 仍成立，且现在有源码级 h_in 公式佐证）
- **替身替代不了的**：h_in 的**用途②（喂专家前向）**——专家吃的就是这个混合向量，
  替身若给出错误的 h_in，专家计算就错
- **可落地窗口（源码指出）**：因为 h_in = Σ probs×summary_k 是「跨 block 混合」，
  而每个 block 内部是 3 层 KDA + 1 MLA，**同一 block 内的 h_in 主要受该 block 自己
  的 summary 主导** → 可用「上一个 block 的 summary + 轻量预测当前 block 内的增量」
  近似（这是"小小替身"最合理的切入点）

## 十、原始 bf16 口径的注意力精确拆解 + 「记忆在线 / 变换离线」双轨（2026-08-28 深夜）

> 本轮把注意力权重按 **原始 bf16（2B/elem，无 MXFP4 水份）** 精确拆解，
> 并给出「替身能否接管、接管给哪部分」的最终分层。
> 修正了旧口径（60/36/16GB 三个数字的变形根因），也修正了 §8.6「KDA 稠密墙
> 完全不可捅」——— 真相是 **KDA 的记忆在状态 S(数据) + 96 标量，qkv/o 是可蒸馏浅投影**。

### 10.1 三口径对齐（为何 60 → 36 → 16）

| 数字 | 口径 | 含义 |
|---|---|---|
| 60~71.6 GB | **原始 bf16 权重**（真实实施） | KDA 65.3 + MLA 6.3 |
| 36 GB | 用户设想 MXFP4 量化**整个 trunk** | 含注意力 + 共享专家 + latent + router + dense |
| 16.8 GB | 36GB 里再按 MXFP4 拆**注意力子集** | 只是「注意力」一小块，非 trunk 全量 |

**MXFP4 尚未实施，算账一律用原始 bf16 口径。** 之前拿 36/16 当基准是错的。

### 10.2 原始 bf16 注意力精确尺寸（源码 shape 实锤）

```
KDA 69层 : 65.29 GB  (每层 946MB = 473M 元素)
  q/k/v_proj: 3 × 7168×12288        (~88M × 3)
  o_proj    : 12288×7168            (~88M)
  conv/A_log/dt_bias/f_a/f_b/b/g   : <1M
MLA 24层 :  6.31 GB  (每层 263MB = 131M 元素)
  q_a/q_b/kv_a/kv_b/o_proj
注意力合计: 71.60 GB = bf16 trunk 108.8GB 的 66%
```

### 10.3 KDA 的记忆核心在「数据」，不在权重(关键)

KDA 递归（论文/源码）：
```
o_t = S_t^T q_t                       # 输出 = 状态 × 当前 query
S_t = (I − βk k^T) Diag(α) S_{t−1} + β k v^T   # delta-rule 状态更新
```
- **状态 S** = 96 头 × 128×128 = 1.57M elem/层 → 全 69 层 **217MB**（bf16，数据非权重）
- **A_log** = 96 标量/层 × 69 = **6624 个标量**（几乎 0 权重）
- **dt_bias** = 12288/层 × 69 ≈ 848K 标量
- ⇒ **KDA 的「记忆/智能」全在状态 S + 96 标量里（数据，运行时成长）**
- ⇒ **其 qkv/o 四个大投影（~946MB/层）只是可蒸馏的浅线性变换，非记忆本体**

### 10.4 「记忆可在线成长 / 变换需离线蒸馏」双轨

**类别 A · 记忆（状态 S 相关）—— 可丢弃权重，在线实时成长**
- KDA 的记忆本来就是状态 S 随序列 `S_t` 更新，与 Q 权重无关
- 丢弃 Q 权重不丢记忆，状态 S 在线上自己「长」
- 只需保留 S 的初始化 + A_log(96 标量) + dt_bias（极小）

**类别 B · 变换（qkv/o 线性投影）—— 不可在线丢，需离线蒸馏**
- q=W_q x, o=W_o attn_out 是必要的输入/输出变换，无权重则 h_in 算不出
- 不能「运行中现长」——只能离线蒸馏成小替身（几百 MB）或保留精简权重
- S 的更新规则本身（delta rule）也是固定算法，非权重

**核心洞察**：KDA 天生「权重轻、记忆随运行成长」——96 标量 + 状态 S 就是它的
在线成长机制。最适合作「在线成长」的注意力。但 qkv/o 变换是「成长土壤换算器」，
丢不得、也现长不了，须离线备好小替身。

### 10.5 替身对「算 route」的真实收益（原始口径）

- 替身让 **KDA 的 h_in 功能**从「读 65.3GB 权重」→「几百 MB 替身 + 217MB 状态 + 6624 标量」
- ⇒ **省 ~64GB/token 的 KDA 注意力读取**（原始口径，量比量化版更大、更可观）
- 剩余墙（原始）：MLA 6.3GB（真全局注意力，替身碰不得）+ trunk 其余 ~37GB
  （共享专家+latent+router+dense+embed+vision）+ 专家 top16 25.8GB
- **主战场不是专家(已顶天)、不是 MLA(1.6GB小)—— 是 KDA 这 65.3GB**

### 10.6 诚实的边界（不能空欢喜）

1. **只覆盖 KDA(69层) = 65.3GB**；MLA(24层 6.3GB) 是替身碰不得的真全局注意力
2. **蒸馏 qkv/o 需真实 (h前, h_in) 激活数据训练 + 复现精度要够**（KDA 输出敏感）
3. **属性是「蒸馏换存储」，非「免费」**：成本从存储转移到训练/精度
4. **喂专家保智力仍要真实 h_in**（尤其 MLA），替身只救「选路」那部分

### 10.7 待验证（数据到手才能判）—— ⚠️ 已封存 2026-08-29（压缩/蒸馏路线整体关闭）

- 蒸馏替身复现 qkv/o 变换的精度（需真实激活对）
- 状态 Ŝ 在线成长与官方 S 的一致性（需运行 K3 导出 S）

## 十一、全模型可蒸性清单 + 蒸馏QAT MXFP4 流程（2026-08-28 深夜续）—— ⚠️ 已封存 2026-08-29（压缩/蒸馏路线整体关闭）

### 11.1 K3 全模型「可蒸性」分层地图（原始 bf16 口径）

> 判定标准：权重是否为「每 token 重复的固定浅变换/记忆在数据」→ 可重学成小网。
> 「蒸馏」= 有损存储、接近无损能力；区别于「低秩换算」（数学上因满秩而不可行）。

| 类别 | 组件 | 原始尺寸 | 可蒸性 |
|---|---|---|---|
| KDA 注意力变换 | q/k/v/o 四投影 | **65.29 GB** | **↑↑ 可蒸（已实锤）** |
| KDA 记忆核心 | 状态S + A_log(96) | 217MB数据+6624标量 | 已是数据/标量，近乎免费 |
| latent 投影 | down/up (7168↔3584) | **9.45 GB** | **↑↑ 可蒸（同类浅变换）** |
| router | gate(7168→896)+corr_bias | 1.18 GB | 本就要算 route，可常驻/可蒸 |
| 共享专家 | 2个全宽MLP/层 | **24.57 GB** | **↑ 中等可蒸（需实测）** |
| MLA 注意力 | q/kv/o (loRA) | 6.31 GB | ↓↓ 不可蒸（真全局） |
| 896 专家 | 每层896专精网 | 5.4TB（只读 top16≈97GB）| 无需蒸（本就稀疏路由） |
| embed+lm_head | vocab 160K 查表 | 2.3 GB | 偏不可蒸（查表/共享优化） |

**可蒸主战场 = KDA 65.3 + latent 9.5 + 共享专家 24.6 ≈ 99.4 GB（原始口径）**
其中 KDA + latent（74.8GB）是「稳的可蒸浅变换」；共享专家（24.6GB）中等可蒸、待实测。

### 11.2 蒸馏 + QAT MXFP4：正确顺序（关键坑）

**两个正交阶段，别混、别反序：**
```
阶段1 · 蒸馏（容量压缩）: 大矩阵 → 小替身（去满秩冗余，「重学」非「换算」）
阶段2 · QAT MXFP4（精度压缩）: 小替身权重 → 4bit（进一步省存储/带宽）
```

**❌ 错误：先 MXFP4 大矩阵，再蒸馏** → 学生学「已坏的老师」，双重误差。
**✅ 正确：先蒸馏出干净的小替身，再对其做 QAT** → 误差单一、可补偿。

**最优形态（一体化）：QAT 感知的蒸馏** —— 训练小替身时学生权重本身就是
MXFP4 量化，蒸馏损失同时含「容量逼近」+「量化可容错」，学生从训练起习惯 4bit
噪声 → 部署时 MXFP4 不掉点。

### 11.3 替身为何比大模型更适合 MXFP4

- 替身是学生，训练时就吃量化噪声（QAT）→ 天然抗 4bit
- 容量小，scale/量化开销占比可控
- 替身每 token 算 route 要常驻/频繁读 → MXFP4 让常驻成本、读取带宽都小，
  正配合 ASIC 的 MXFP4 硬件通道

### 11.4 工程链路（老前提绕不开）

```
① 跑真 K3 (WSL2) → 导出 (h前, h_in, top16) 激活数据集
② 用数据集做 QAT 蒸馏 → 得 MXFP4 小替身（几百MB, 4bit）
③ 部署：小替身算 route + 状态S(数据)在线成长 → 不再需要 65.3GB KDA
```
**前提不变：蒸馏 + QAT 都需真实激活数据，须先跑真 K3 收集。**

### 11.5 无损压缩的裁决（防走回头路）

- 「无损压缩」省 10-20%（权重满秩、近均匀、最大码仅17%，熵增益小），
  且要增 hardware decoder/延迟/面积，对 61.8GB 带宽杯水车薪
- 「无损能力」（推理输出不变）才真正该要 → 蒸馏是「存储有损 99.7%、
  能力接近无损」的正解，不是信息论无损压缩
- **存储无损 ≠ 能力无损；过度压缩反致输出有损**
- 方向裁决：别回「无损压缩」死胡同，走「能力无损的蒸馏」

## 十二、「两端都要」替身撞上满秩墙 + 自蒸留现成工具链（2026-08-29）

### 12.1 决策更新：替身「两端都要」（选路 + 复现 h_in 喂专家）

- 复现 h_in = 必须近乎无损逼近 qkv/o 满秩变换 + 状态 S

### 12.2 满秩墙（纯 Python 数值证实）

- KDA 的 q/k/v/gate/out 是**全宽 d→d（K3 甚至 7168→12288 升维）线性映射**
- 满秩 d→d 映射「有效秩≈d」：前 5% 维度仅捕获 5% 能量（低秩近似丢 95%）
- ⇒ 要近乎无损复现 h_in，替身内部秩须接近满秩 d → **缩不到几百MB**
- **与 §8.6 呼应**：真实权重满秩、谱均匀、压不动（纸面可压，真实推开）
- 即「两端都要」的替身，**不是存储换蒸馏能白拿的** —— 复现 h_in 是硬秩需求

### 12.3 出路（在「两端」之间切一刀，而非两者全包）

- **若替身只做用途①(选路)**：只需 logits/top16 近似对 → 可小(几十MB)，

- ⇒ 最优分层：**替身救「选路」(小) + 真 KDA/注意力保「h_in」(精准)**
  —— 这才是「两者都要」的正确实现：不是同一个替身做两件事，
  而是「小替身选路 + 真身(或分块缓存)产 h_in」

## 十三、「张量/头结构分解」绕过扁平满秩墙 —— 判"要不要蒸馏"的关键(2026-08-29)

### 13.1 认知修正: 满秩墙只挡"扁平SVD", 不挡"头结构张量分解"

> ⚠️ **被 8-29 真 K3 实测否定**：§19.1 实测 head_err_R4≈0.98-0.99（远超判据 0.1），头间共享基**不存在**，头结构张量分解同样撞墙。本节纯 Python(smol 尺寸)结论不可外推到真 K3。仅存档。

- 上轮 §12"复现h_in缩不动"的结论, 只对「把矩阵当扁平SVD截断」成立
- KDA qkv 是 [H头, HD, d] 天然张量结构(smol q_proj=Linear(d,d), reshape成头)
- 纯Python验证(smol尺寸 H=5,HD=64,d=320):
  - 若头间共享低秩基 r=4: 参数 102400→2560 (2.5%, 40x), 重构误差 1.5e-16 零误差
  - 即「头结构可压低秩基 → 张量分解可行 → 不撞扁平满秩墙」

### 13.2 张量分解 vs 蒸馏: 谁替代谁

- 张量分解: 无损/近无损的"存储编码"——把稠密矩阵换成低秩因子, 只省存储/带宽
  - 若 KDA 分解后能在 ASIC 上直接跑 → **确实不需要蒸馏替身**(用户判断部分成立)
- 蒸馏: 有损的"功能压缩"+可换更轻的非线性算子(省算力/延迟, 非仅存储)
- ⇒ 张量分解不能替代蒸馏的"换算子"那部分, 但能替代"缩存储"那部分
- ⇒ 张量分解让"是否需要蒸馏"成为真选项: 够小→直接跑本体; 不够/嫌慢→再蒸馏

### 13.3 判定脚本: tools/kda_head_sharing.py (一次判定要不要蒸馏)

- 输入: 真实 KDA 层 q/k/v 权重 + (H, HD, d)
- 输出两个判定量:
  1. 扁平SVD有效秩(捕获90%能量需保留多少行) → 扁平能否压
  2. 头结构rank-R共享基重建误差 → 头是否强共享 → 张量分解能否压
- 分叉:
  - 头共享度高(重建误差小) → 张量分解可行 → **可能不需要蒸馏**
  - 头间独立(误差大) → 张量分解死 → **必须蒸馏**
- 用法: python3 tools/kda_head_sharing.py --ckpt model.safetensors --H 5 --HD 64 --d 320
- 注意: Per-Head Muon(每头独立牛顿-舒尔兹正交化)暗示可能鼓励头间独立, 对张量分解不利
  —— 这正是真实权重要测的点

### 13.4 现在能测 vs 测不到(诚实)

- 能测(本机, 纯数学): 张量分解结构可行性 → 已证: 可行, 可40x+, 零误差
- 测不到(本机): 真实 K3 的 qkv 头间是否真共享低秩基 → 数据依赖, 须真实权重(torch机)
- ⇒ "现在就可以测吗"的答案: 判定脚本已备好, 但真实压缩比须 WSL2 带权重跑一次

## 十四、头间无共享的出路: 公共基投影(本质即张量分解CP/Tucker)(2026-08-29)

> ⚠️ **被 8-29 真 K3 实测否定（§19.1）**：head_err_R4≈0.98-0.99 → 头间共享基不存在，§14.2 的"公共基投影可行"与实际数据冲突。仅存档。

### 14.1 失败模式排序(张量分解为何"不行",提前预警)

1. **头间无共享(最可能,难防)** — K3/smol 用 Per-Head Muon(每头独立牛顿-舒尔兹正交化)
   训练设计刻意让头子空间独立/正交。若头真独立→ [H,HD,d] 张量各头满秩→压不动
2. 低秩截断踩到"末位奇异值仍有任务信息" → 掉点(§8.6 复现:纸面能压真实掉点)
3. 理想共享基(r=4零误差)是合成假设; 真实 r 需大到近原宽才不掉点→等效白压
4. 张量分解把一次大矩阵乘拆成R步小因子, 若ASIC是单次大乘法器→吞吐/延迟反降
5. 覆盖不到: 状态S(数据,217MB)+embed(行独立)不受张量分解影响 → 需量化/别指望

### 14.2 头无共享 ≠ 死路: 公共基投影可行(方向对)

- 现实: 注意力头功能高度冗余(剪枝/合头研究证实), Per-Head Muon保正交性, 不等于功能无关
- 操作: 对96头列空间做全局PCA → 得公共基, 把每头投影进前R方向(替换原头)
- 可行性: 若96头功能冗余高(公共基捕获大部分能量), 且投影误差 < 任务容忍 → 可行不掉点
- 关键: 这不是"头间真共享"的运气, 而是"找公共方向"的主动构造

### 14.3 重要澄清: 公共基投影 = 张量分解本义, 非退路

- CP/Tucker 分解的核心就是"找共享模式/公共方向"
- 所以"头无共享时先PCA找公共基"**就是张量分解的做法**, 不是失败后的自救
- '默认有共享基' vs '主动PCA找公共基' 是同一方法的两种假设强度

### 14.4 公共基投影的两个硬约束(诚实)

1. 投影=有损: 误差>0。只选路(误差容忍大)几乎必胜; 复现h_in(误差敏感)公共基须大→收益小
2. KDA智力在状态S, qkv只是读写门; 若头真独立恰说明每管不同记忆子空间,
   '共性'可能已在S中合并 → qkv里硬找共性收益有限
3. 省的是"输入共享部分"的带宽, 每头尾投影仍在 → 非全部带宽

### 14.5 判定: kda_head_sharing.py 第2项已隐含测冗余

- rank-R共享基重建误差小 → 公共基够 → 可行
- 误差大 → 冗余不足 → 难以"找公共基"压
- 须真实权重(torch机/WSL2)跑一次才能定死 14.1 vs 14.2 何者成立

## 十七、护城河定位修正: 系统方案, 非算法(2026-08-29)

### 17.1 张量分解不是黑科技(用户警惕成立)
- SVD/Tucker/CP 是70年经典数学, 在LLM压缩/推荐/信号处理用了几十年
- 在LLM上做张量分解压缩是公开领域(GPTQ/TFLite等), K3官方训练也在用低秩/张量技巧
- ⇒ 算法层面无护城河, 官方随时能做

### 17.2 官方"不会给你机会"的真因 = 痛点/场景独占, 非技术独占
- 官方数据中心GPU集群: 内存/HBM/带宽不是瓶颈 → 张量分解收益趋近零 → 无动力做
- 你的ASIC卡NAND带宽 → 极其特定硬件痛点, 通用服务器推理不痛
- ⇒ 官方不做, 不是做不到, 是没动机

### 17.3 真正护城河 = 垂直系统整合, 非单个算法
- 别人也会张量分解(算法无壁垒)
- '为NAND带宽受限定制ASIC, 做KDA专用张量分解+部署管线' = 垂直系统工程
- 需懂KDA结构+懂ASIC访存+懂MoE部署+工程落地 = 组合稀缺
- 类比: 会用SQL≠数据库公司, 会用CUDA≠芯片公司

### 17.4 定位修正(关键)
- 别把产品定位成"张量分解工具"(无壁垒, 官方随手做)
- 定位成"特定硬件的KDA/MoE部署压缩方案"(有护城河)
- 故事讲"垂直系统", 不是"算法"
