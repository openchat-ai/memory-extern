# 108.8GB 的隐藏税单：我在 MoE 推理架构里踩过的坑

> 用 32GB 内存的台式机跑 1.5TB 的 Kimi K3，我发现了每个 token 都要为一条被忽视的通路买单。

## 背景

Kimi K3 是月之暗面（Moonshot AI）于 2026 年 7 月发布的旗舰开源模型。2.8 万亿总参数，每个 token 激活 104B 参数。架构基于三项核心创新：

- **KDA（Kimi Delta Attention）**：混合线性注意力，93 层中 69 层用 KDA、24 层用 Gated MLA，3:1 比例交错。KDA 维持固定大小的循环状态，支持 100 万 token 上下文
- **Attention Residuals（AttnRes）**：将 93 层分为 8 个 block，block 间用注意力机制选择性检索前序层表征，而非简单残差累加
- **Stable LatentMoE**：896 个专家中每个 token 激活 16 个，通过 Quantile Balancing 和 SiTU-GLU 保持极高稀疏度下的训练稳定

量化方案：从 SFT 阶段起应用量化感知训练（QAT），MXFP4 权重 + MXFP8 激活。总权重文件 1.56TB（96 个 safetensors 分片）。

MoE 推理的核心承诺是稀疏性——2.8T 的模型，每个 token 只激活 104B 参数，只需读一小部分权重。所有关于 MoE 的讨论都在说：稀疏是好事，省带宽，能跑大模型。

我把这套说辞当真了，然后在一个 32GB 内存的台式机上实际跑了一遍。发现了一条所有人都忽视的通路，每个 token 要为它额外付出 108.8GB 的带宽。

以下是这 108.8GB 是怎么来的，以及它如何改变整个推理架构的账本。

## 第一笔账：专家流量（已知，但需要实测验证）

K3 的专家结构在官方技术报告中已有描述。我用 safetensors header 扫描做了逐字节验证：

- 93 层（92 层 MoE + 1 层 dense layer0）
- 每层 896 个专家，top-16 被激活
- 单个专家：w1 [3072, 7168] + w2 [3584, 6144] + w3 [3072, 7168]，MXFP4 量化态 **17.55 MB/层**
- 每 token 激活流量：92 × 16 × 17.55MB = **25.83 GB**

这笔账很干净。稀疏性确实生效了——1.45TB 的专家池，每个 token 只读 25.83GB，约 1.8%。

到这里一切正常。官方文档也描述了这个稀疏度。**问题出在专家以外的部分。**

## 第二笔账：108.8GB 的幽灵（实测发现）

我用 kimi-k3-in-c 引擎在一台 32GB 内存的台式机上实际跑通了 K3。HDD，72MB/s，首 token 27.5 分钟。慢是意料之中的——但运行时统计里出现了一个我没有预算的数字：

```
trunk 全读：870.5 GB = 8 × 108.8GB
```

**每个 token 重读了 108.8GB 的 trunk 权重。**

什么是 trunk？就是除 routed experts 以外的所有权重：KDA 层的循环门控投影、Gated MLA 层的 Q/K/V/O 投影、2 个共享专家、router gate、dense layer0、embedding、vision encoder、mm_projector。这些权重在每一层、每一个 token 的前向传播中都会被用到。

但没有人把它们算进"每 token 流量"。因为——

> 在 GPU 上，trunk 常驻显存，流量为零。
> 在 32GB 内存的台式机上，trunk 装不下，每个 token 从盘上重新搬一遍。
> 这 108.8GB 不是 bug，是内存墙的产物。

**这就是 MoE 推理里被忽视的"稠密税"：专家有稀疏红利（只读 1.8%），trunk 没有（100% 全用）。**

补充一点：K3 的注意力机制是 KDA（线性注意力）而非标准 softmax。KDA 维护固定大小的循环状态，KV-cache 不随上下文长度增长。但 KDA 层的权重本身（循环门控投影矩阵）仍然每 token 每层都要读——这部分就是 trunk 税的来源之一。

## 第三笔账：名义精度与实际存储（实测验证）

官方文档明确写了"MXFP4 weights with MXFP8 activations"和"量化感知训练"。这不是事后压缩，是训练时就考虑了低精度。

但**名义精度和实际落盘字节是两回事**：

实测落盘密度：**2.12 bit/weight（含 scale）**。

K3 把 MXFP4 尾数压到了 2-bit 索引编码：

- 每 64 个权重共享一个 scale（U8）
- 组内每个权重只存 2-bit 索引（4 值/字节打包）
- 语义上还是 MXFP4 格点值，但存储成本只有 2.12 bit

这意味着：**说"4-bit 量化"的人在说名义，说"2.12 bit"的人在说现实。** 用名义精度估算带宽，会高估一倍流量。

## 做了什么

### 实测验证

所有参数不是纸上推导，是逐字节验证：

- safetensors 全量 header 扫描：96 分片，497,220 张量，data_offsets 不越界
- kimi-k3-in-c 真实推理：生成 "Hello, I am a 20 year old"，运行时统计与裁决数逐项吻合
- 路由轨迹分析：100K 条真实请求，90% 重复访问，触及池子 12.14%

### RTL 验证

在 Tang Mega 138K（国产 GW5AST-138 FPGA）上搭建了完整的数据通路：

- 128 路 SIMD MAC 阵列：移位加法替代乘法器，零 DSP 占用
- 7 级归约树 + 饱和累加器（ACC16/ACC32 双模式）
- 向量化 SiTU 激活（官方用 SiTU-GLU，不是 GELU）
- PCIe DMA 引擎（AXI-Stream 协议）

所有模块通过 Verilator lint + 仿真验证。

**关键发现：MXFP4 的 2-bit 索引编码对 FPGA 极其友好。** 每个权重只需一个 256×4 的查找表解码，比传统 bf16 乘法器便宜 30 倍。同一个 FPGA 上可以堆出 500+ 等效通道。

### 流量建模

写了 `batch_traffic_model.py`，用真实路由轨迹拟合并集增长曲线：

> ⚠️ 下表为 **trunk 36GB 量化假设**下的旧口径；2026-08-29 定案 trunk 保 fp16 后，每 pass 流量应改用 108.8GB/pass 重算（单聊 ~0.17 t/s 结论不变）。

| batch | 每 pass 流量 | Gen3×8 | SerDes 全开 |
|---|---|---|---|
| 1 | 61.8 GB | 0.11 t/s | 0.17 t/s |
| 128 | 68.2 GB | 13.1 t/s | 19.9 t/s |
| 512 | 87.5 GB | 41.0 t/s | 62.0 t/s |

单聊很慢（61.8GB/token 的物理限制），但 batch 场景下并集增长 + trunk 共享让吞吐快速爬升。

### Trunk 量化（已否决）

> **定案 2026-08-29：trunk 保留 fp16（108.8GB/pass），量化口径 36GB 作废。** 详见 `k3-verdict.md` 与 `independent-stack.md` B.9-B.12。
>
> 早期曾设想把 trunk 从 ~110GB（原始精度）压到 **36GB**（MXFP4 同款 QAT 方案），每 token 总流量从 134.6GB 降到 61.8GB —— 但 trunk 的 dense 投影（残差直通、每层必经）量化误差沿链爆炸，4-bit 重建误差 17.4% vs int8 0.96%（~18x）直接否决。质量验收不存在：这条路没走通，也不该走。

## 学到的三件事

**1. 不要在 GPU 的世界里思考推理架构。**

GPU 上 80GB 显存让 trunk 常驻，所以没人讨论它。但在内存受限的设备上，trunk 是最大的带宽杀手。架构设计的第一步是搞清楚"什么必须流动，什么可以驻留"——这个问题的答案在不同硬件上完全不同。

**2. 读文档比自己猜重要。**

K3 的架构细节（KDA、AttnRes、SiTU-GLU、QAT）全部写在官方技术报告里。我没读就上手，结果激活函数写错了（以为是 GELU），注意力机制搞混了（以为是标准 softmax）。这些错误直接影响了 FPGA 解码器的设计方向。**先读文档，再动手。**

**3. 实测比模型值钱。**

每一个翻案（缓存从 ×5 变 ×1.55，投机从 ×3 变 ×1.26，熵编码从 +15% 变 +7%）都是真数据推翻纸面推演。没有 kimi-k3-in-c 的运行时统计，我们会在错误的假设上走很远。

## 诚实的结论

这套架构在 FPGA 板卡上跑不出可用的单聊速度（0.17 t/s）。这是物理限制——61.8GB/token 经过任何 PCIe/SerDes 管子都到不了秒级。

它的价值不在速度，在于：
- 证明了流式 MoE 数据通路的正确性
- 给 ASIC 设计提供了实测参数（流量、并集增长、缓存命中率）
- 用一块 1000 元级国产 FPGA 板完成了需要 ¥30万 GPU 才能做的实测

**NAND 合封 ASIC 的路径依然是唯一解：把存储焊在计算旁边，消除总线瓶颈。** FPGA 是通向那里的验证工具，不是终点。
