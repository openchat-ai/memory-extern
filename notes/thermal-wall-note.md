## 0. 立项理由：为什么手机是干净载体

PC 侧 `BUSINESS-VERDICT.md` 的级联是「低速盘→高速盘→内存」三档，介质级联与 cache 争抢缠在一起，
半年才靠真机拔条实验分清算力墙 vs 带宽墙。**手机是统一内存，只有一档 DRAM** —— 变量被物理消掉，
且已发表的移动端测量论文（2410.03613 / 2505.06461 / 2607.05475）**均只报 t/s 与能耗，
无一篇报"每 token 搬运字节 / 带宽利用率"**。这个空位就是本项目的切入点。

**但首测证明了一件事：移动端的第一限制不是带宽，是功耗/调度收缩。**

## 1. 字节账（逐字节，非估算；降频不变）

来源：GGUF 文件真实落盘 + GGUF 头逐字段读架构。

| 项 | 值 |
|---|---|
| 模型 | Qwen2-0.5B-Instruct **Q4_0** |
| GGUF 落盘 | 352,969,408 B = **336.62 MiB** |
| 总参数（llama-bench 自报） | 494.03 M |
| 实际密度 | 5.716 bit/param（标称 Q4=4bit，实际更高 —— 已计入下面的份额法） |
| 架构（GGUF 头读出） | qwen2 / 24 层 / hidden 896 / FFN 4864 / **GQA 14:2，kv_dim=128** / ctx 32768 |
| block 参数 | 24×(attn 1,835,008 + mlp 13,074,432) = **357.83 M**（占总 **72.4%**） |
| **单 token decode 搬运** | 落盘 × 72.4% = **243.81 MiB**（255,656,193 B） |

**自洽性校验**（这一条必须有，否则数字无意义）：
- block 参数 357.83M < 总参数 494.03M ✓
- 占比 72.4% 符合 Qwen2-0.5B 的 tied-embedding 结构（余 136.20M 为 embed，decode 不逐 token 读）✓
- 份额法自动吸收 Q4_0 的 fp32-norm 标度偏差，不需要手算 bit 数 ✓

**要点：字节是常量，降频与 t/s 波动都不改变它。** 这是本判据的立足点。

## 3. 已识别的三个污染点（**这三点不可用，教训必须留档**）

### 3.1 点 7/8/9：t/s 崩到 0.61–2.20，不是温控

同期温度 57.8–61.8°C（与前后无异），但**可用内存从 2256MB 涨到 2898MB** —— Android 后台在动，
叠加首次测试期我自己的其他命令，产生内存回收/换页。**归因：内存干扰，不是功耗墙。**

→ 处置：这三点剔除。后续用 `tps_spread`（每点多跑取极差）自动标记，`spread > tps×0.5` 即污染。

### 3.2 温度与 t/s 不单调相关 —— "温度越高越慢"在本数据不成立

- 点 10 温度最低（44.5°C）但 t/s 仅 5.85

起始即 57.4°C。**没有冷机起点，"衰减曲线"只有衰减段、没有基准段。**

## 4. 首测真正的发现（剔除污染后仍成立）

**同温度带内 t/s 掉 36%：**

> ⚠️ **本节结论已于 §5b 降级。** 下列 −36% 是在**噪声摆幅 27.7°C** 的数据上算出的，
> 且温度列实际测的是空闲区而非负载区。**该数值不可引用**，请改用 §5b.5 的 −18%/+4.6°C。
> 本节仅作过程留档。

| 段 | 温度 | t/s | 带宽 |
|---|---|---|---|
| 前段 0–6 | 57.8–62.6°C | 15.15–16.93 | 3.87–4.33 GB/s |
| 后段 11–14 | 60.2–62.6°C | 10.02–11.71 | 2.56–2.99 GB/s |

温度几乎不变（都在 57–63°C），t/s 从 16.93 → 10.79（−36%）。字节恒定 243.81 MiB，
所以带宽利用率同步下降。**但如上，此归因不成立** —— 温度测量本身有问题。

**这不是热墙。** 冒烟测试（`-r 3`）补上了关键证据：

| 点 | 温度°C | **CPU 平均 MHz** | t/s |
|---|---|---|---|
| 0 | 68.9 | **1289** | 13.11 |
| 1 | 68.1 | **1243** | 14.18 |

**温度 68°C（离 90°C 热极限尚有余量），CPU 却只跑 ~1.28 GHz。**
而静置态实测各核频率 787–2496 MHz 不等（大核/小核异构）。

→ **结论修正：限制因素是功耗/调度收缩（Android scheduler 主动压频 + DVFS），
  不是纯热墙，也不是带宽墙。** 字节账在此的用处正是把"带宽"这一项钉死为常量，
  从而把残差（时间变长）干净地归给功耗。

**频次提示**：`cpu0/cpufreq/cpuinfo_max_freq` 报 1804 MHz，但静置时 cpu4/5 已达 2496 MHz
→ 该机频率上限是动态的，**不能用 `cpuinfo_max_freq` 当峰频**；采集须用实测 `scaling_cur_freq`。

## 5. 与公开数据的差距（先记账，避免误判方向）

| 来源 | 条件 | decode t/s | ÷ 本机稳态 10.79 |
|---|---|---|---|
| 官方 llama.cpp Snapdragon 文档 | **1B**，CPU 路径 / GPU 路径 | 47.6 / 51.6 | 4.4× / 4.8× |
| arXiv 2607.05475（400 组实测） | 4 款骁龙 × 5 框架 × CPU/GPU/NPU | 20–70 | 1.9×–6.5× |
| arXiv 2505.06461 | iPhone 15 Pro，**1B**，**CPU-only 胜 GPU** | 17（vs GPU 12.8） | 1.6× |
| **本机首测（热态+后台干扰）** | SM7475 7+Gen3，**0.5B** Q4_0 | 15.15–16.93（峰值段） | 1.4×–1.6× |
| **本机稳态后段** | 同上，持续满载 | 10.02–11.71 | 0.9×–1.1× |

**差距实为 4.4–4.8×（对官方 1B 数据），不是我先前口述的 10–15×。已更正。**

**且这 4.4× 不能全记在"温度/内存"账上**，混杂至少三个未分离变量：
1. **模型规模不同**：官方/arXiv 是 **1B**，本机 **0.5B**。0.5B 单 token 搬运更少，**本应更快**，
   方向与观测相反 —— 说明存在**本机特有的更大压制因素**，尚未分离。
2. **SoC 档次不同**：骁龙 8 Elite Gen5（arXiv 上界）vs 本机 7+ Gen3。
3. **起点热态 + Android 后台干扰**：本机首测非冷机、非纯净。

→ **结论：现有数据不足以归因。** 4.4× 是"未分离变量的合成差距"，
不能写成"温度导致"。分离方法见 §7 待办（冷机曲线 + 1.5B 对照把规模变量拉齐到 1B）。

**一条重要的反面证据**：arXiv 2505.06461 证明手机 **CPU-only 常胜 GPU**
（decode 是 memory-bound，CPU/GPU 抢同一条 DRAM 带宽）。
本机 Adreno 的 Vulkan ICD 在 `/vendor/lib/hw/vulkan/` 与 `/apex/...vndk.vulkan/` 均不可见，
termux 内 GPU 路径暂不可用 —— **但按上述文献，CPU 路径恰是更干净、也更该用的那条。**
即"跑不动 GPU"对本课题不是障碍。

## 5b. 测量方法自身的错误与修正（本轮最重要的一节）

### 5b.1 症状：静置曲线温度乱跳 27.7°C

`results/thermal/cooldown.csv`（33 点 × 15s = 11.6 min 纯空闲）显示温度在 **41.2–68.9°C** 反复横跳，
最大摆幅 **27.7°C**，同期频率 1001–2162 MHz 同步乱跳。**噪声远大于待测效应，数据不可用。**

### 5b.2 根因：取全局 max 采到了与负载无关的区

用对照实验标定（跑 llama-bench 期间看哪些区跟着涨）：

| 分类 | 区号 | 表现 |
|---|---|---|
| **负载上涨区** | **73, 78, 62, 75, 0, 77** | 负载下 4s 内涨 +0.2~0.7°C（约 40°C 档） |
| **空闲高温区** | **36, 32, 30, 44, 27, 26** | 负载结束后仍 48–58°C（约 50–58°C 档） |

**两组完全不重叠。** 原脚本取全局 max，而空闲高温区数值更大，
故 §2/§3 全部数据的"温度"实际**主要在测空闲区**——**噪声是测量方法自造的，不是设备噪声。**

→ 已修正 `tools/thermal_throttle_curve.py`：`LOAD_ZONES=(73,78,62,75,0,77)` 单独取，
`IDLE_ZONES` 仅作环境参考另列 `temp_idle_c`，不再混入主变量。

### 5b.3 修正效果（同一台机、同一模型）

| | 修正前（全局 max） | 修正后（仅负载区） |
|---|---|---|
| 温度摆幅 | **27.7°C** | **4.6°C** |
| 温度区间 | 41–69°C（跨两个物理区） | 41.0–45.6°C（单一物理区） |

**噪声降低 6 倍，已压到待测效应量级以下。**

### 5b.4 附带收获：采集间隔可大幅压缩

原方案 `-i 60`（10 分钟一条曲线）源于"等降温"。实测降温 **1.64°C/min** 且负载区升温极快，
故 **`-i 5` 即足够**：10 点 × 5s ≈ **2 分钟**出一条曲线。
**"10 分钟"是早期把噪声当信号时的过度设计，已废弃。**

## 5c. 频率列的第二次修正：异构 + 调度派活（未完全解决）

### 5c.1 核型实测（`cpuinfo_max_freq`，逐核）

| 核 | 上限 MHz | 组别 |
|---|---|---|
| cpu0–cpu3 | **1804** | 小核 |
| cpu4–cpu6 | **2496** | 大核 |
| **cpu7** | **2918** | prime（唯一最高） |

**8 核异构，且能力相差 1.6 倍。** 故 8 核平均必然失真 → 改为分组采集：
`prime_mhz`(cpu7) / `big_mhz`(cpu4-6均值) / `little_mhz`(cpu0-3均值)，并加 `prime_pct`(占自身上限%)。

### 5c.2 修正效果：符号转正，但仍未找到干净主变量

原始账：`results/thermal/curve_freqfix.csv`（8 点 × 5s，`-g 48 -r 2`，剔除后 8 点全留）。

| 变量 | §5b（8核平均） | §5c（分组） |
|---|---|---|
| corr(频率, tps) | **−0.636（反常）** | **+0.680（正常）** |
| t/s 范围 | 10–13 | **16.2–21.1** |

**符号已转正，方向正确（频率高→快）。但仍不可用作主变量**，理由：

| 观察 | 含义 |
|---|---|
| `prime_mhz` 仅 3 个离散值 {787, 2477, 2592} | **非单调**，是"调度器把活派给了谁"，非热收缩 |
| `prime_pct` 低至 **27%**（787/2918） | **cpu7 约 2/3 时间在闲置**，llama-bench 的 8 线程活主要派给 cpu4/5/6 |
| `corr(big_mhz, tps) = −0.843` | **实际算力核仍反常** —— 与 5c.1 的派活不均一致，非温度所致 |

**根因比"平均"更深**：Android `walt` 调度器在异构核间动态迁移任务，
单核/组均频率反映的是**派活策略**，与**热收缩**混叠。

### 5c.3 副产品：t/s 整体上移 50%+

t/s 从 10–13 提升到 **16.2–21.1**。原因未分离（可能与负载区温度更低、
§5b 修正后干扰减少有关），**但这使"温度是主变量"更难成立** ——
因为本轮 temp 摆幅仅 **1.8°C**，t/s 却跨 16.2–21.1，**t/s 变动远大于温度变动**。

→ **诚实结论：目前唯一稳健的因果量是 `temp_c`，但其解释力被 t/s 内部噪声削弱。
  频率路线未走通，需读调度统计（如 `/proc/.../schedstat` 或 CPU busy time）而非频率。**

**未做**：调度器任务迁移/CPU busy 统计采集。

## 5d. 频率路线失败后的转向：归一化 CPU 账（**目前唯一干净的判别量**）

### 5d.1 沙箱限制：调度统计不可读

| 源 | 结果 |
|---|---|
| `/proc/stat`（全局 jiffies） | `Permission denied` |
| `/sys/devices/system/cpu/cpufreq/policy*/stats`（walt 运行时长） | 文件存在但 `size=0`，不可读 |
| `/sys/devices/system/cpu/cpuidle/state*` | 枚举到 0 个 state |
| **`/proc/<pid>/stat`（本进程 utime+stime+cutime+cstime）** | **可读 ✓** |

→ 故只能测本进程子树；因 llama-bench 全部 8 线程均为本进程子线程，
**cutime/cstime 已覆盖其全部 CPU 时间**，对本实验足够。

工具：`tools/norm_cpu_ledger.py`（边跑边 50ms 轮询累积 —— 首版只在起止读两点，
子进程提前退出即得 `None`，实测 `cpu_s=-1`，已修）。

### 5d.2 核心思想：CPU 秒 / token 是**归一化**的量

字节恒定 243.81 MiB/token（§1），故若 t/s 变化源于**算力被压**，
则每 token 需**更多 CPU 秒**去补偿；若源于**内存/等待**，CPU 秒/token 应**不变**。
**这是频率给不出的判别力** —— 频率受派活策略污染，CPU 秒不受。

### 5d.3 实测（6 点 × 48 tok，间隔 5s）

原始账：`results/thermal/norm_cpu.csv`

| 点 | temp_c | t/s | cpu_s | wall_s | tokens | **cpu_ms_per_tok** | 带宽 GB/s |
|---|---|---|---|---|---|---|---|
| 0 | 39.5 | 12.27 | 30.79 | 5.00 | 61 | 502.35 | 3.137 |
| 1 | 40.5 | 10.77 | 35.01 | 5.66 | 61 | **574.60** | 2.753 |
| 2 | 41.2 | 10.51 | 35.04 | 5.61 | 59 | **594.80** | 2.687 |
| 3 | 41.5 | 15.16 | 27.47 | 4.44 | 67 | **408.04** | 3.876 |
| 4 | 41.5 | 14.29 | 26.78 | 4.29 | 61 | 436.79 | 3.653 |
| 5 | 41.7 | 12.61 | 30.23 | 4.85 | 61 | 494.80 | 3.224 |

`cpu_s`(26.8–35.0s) > `wall_s`(3.5–5.7s) ⇒ 多核并行，符合 8 线程，账实自洽。

### 5d.4 判别结果：等比缩放 = 纯算力波动

```
corr(tps, cpu_ms_per_tok) = -0.9932      ← 近乎完美反相
corr(tps, temp_c)         = +0.4006      ← 弱，且为正号
t/s 差 1.44×  ⇔  cpu_ms/tok 差 1.46×     ← 基本等比
```

| 观察 | 含义 |
|---|---|
| `cpu_ms/tok` 与 t/s **近乎完美反相（−0.9932）** | t/s 波动**不是**内存/等待造成 |
| t/s 与 cpu_ms/tok **等比（1.44× : 1.46×）** | **纯算力缩放** —— 无固定开销混入 |
| `cpu_s` 与 t/s 反相（27.5s↔15.16，35.0s↔10.51） | 慢时**烧更多 CPU 时间**，符合降频后需更多周期 |
| 温度相关性仅 +0.40 且**为正** | 本轮温度（39.5–41.7°C）**非**主变量 |

→ **本轮 t/s 的 10.5–15.2 波动，归因于算力（CPU 周期供给）变化，非内存、非等待、
  且温度在此区间内无解释力。** 这是本项目迄今最硬的一条归因。

### 5d.5 对前序结论的连带修正

| 前述说法 | 修正后 |
|---|---|
| §5b.6「温度是主变量，corr −0.788」 | **不成立**。本轮 temp 区间仅 2.2°C、corr +0.40（正号）。−0.788 系同温度带内比较，易受混杂 |
| §5c「频率路线未走通」 | 确认。根因是**派活策略**，非热收缩；已换 CPU 秒/token |
| 「t/s 变动远大于温度变动（§5c.3）」 | **得到解释**：t/s 跟随算力走，温度只是伴随 |

### 5d.6 仍未回答（诚实边界）

**是什么在改变算力供给？** 本轮只证明"是算力"，未证明"因何"。
候选（均未分离）：walt 派活策略随负载迁移、DVFS 对负载的响应、
后台任务竞争、**本轮区间温度过低（39–42°C）不足以触发热收缩**。

→ 需**主动加压**（拉到 55°C+ 区间）才能验证是否热收缩。这是下一步唯一必要实验。

## 5e. 加压实验：等比缩放确认（**本项目迄今最硬的一条账**）

原始账：`results/thermal/stress.csv`（连续 12 次 × 96 tok，`-r 1`，点间无间隔以持续升温）

| 点 | temp_c | t/s | cpu_s | **cpu_ms_per_tok** |
|---|---|---|---|---|
| 0 | 42.2 | **15.20** | 47.97 | **422.6** |
| 1 | 43.0 | 14.10 | 50.37 | 459.4 |
| 2 | 44.7 | 11.23 | 61.16 | 570.8 |
| 3 | 45.9 | 9.90 | 69.11 | 648.2 |
| 4 | 46.4 | 4.60 | 135.18 | 1314.6 |
| 5 | 46.6 | 2.52 | 238.43 | 2310.6 |
| 6 | 46.3 | **2.29** | **265.96** | **2545.0** |
| 7 | 46.9 | 6.95 | 100.21 | 894.4 |
| 8 | 47.3 | 3.91 | 146.57 | 1430.6 |
| 9 | 47.1 | 8.52 | 80.96 | 730.7 |
| 10 | 47.1 | 6.82 | 99.55 | 915.5 |
| 11 | 47.0 | 5.25 | 128.21 | 1182.0 |

### 5e.1 等比缩放（关键判据）

```
t/s:          15.20 → 2.29   降 6.64×
cpu_ms/tok:  422.6 → 2545.0  升 6.02×      ← 与 t/s 等比
corr(tps, cpu_ms_per_tok) = -0.8631
```

**t/s 降 6.64× 时，每 token 所需 CPU 时间升 6.02× —— 基本等比。**
这**排除**了"内存/等待/固定开销"解释：若有非算力因素，等比会破。
**t/s 的全部波动可归因于算力供给变化。**

### 5e.2 温度只动 5.1°C，CPU 时间却涨 5.5 倍

| 量 | 起 → 止 | 变化 |
|---|---|---|
| `temp_c`（负载区） | 42.2 → 47.3°C | **+5.1°C** |
| `cpu_s`（CPU 时间总量） | 47.97 → 265.96 s | **×5.5** |
| `cpu_ms_per_tok` | 422.6 → 2545.0 | **×6.0** |

**温度升 5°C 而每 token CPU 时间升 6 倍 —— 温度的边际效应远不足以解释。**

### 5e.3 结论（本档最强的一条）

1. **算力供给是唯一变量**，且被归一化 CPU 账精确捕获（等比 6.64:6.02）。
2. **不是带宽墙**：字节恒定 243.81 MiB/token（§1），带宽随 t/s 等比下降，
   说明 DRAM 未被压满 —— **墙不在带宽**。
3. **不是温度主导**：+5.1°C 换不来 ×6 的劣化；本区间（42–47°C）远低于热极限。
4. **最可能的机制**：Android `walt` 调度器在异构核间的**派活劣化 / 迁核开销**
   （与 §5c 观察到的 `prime_pct` 低至 27%、cpu7 长期闲置一致），
   或 CPU 时间被**非推理任务**（后台/系统）挤占。
   → **已由 §5f 绑核实验分离：属前者（派活劣化），非后台挤占。**

> **方法论价值（本档真正可发表的部分）**：
> "字节账恒定 → 排除带宽；CPU 秒/token 等比 → 确认算力；温度变化量级不足 → 排除热主导。"
> 这三步构成一个**可复用的判别框架**，且每步都只用本机可读量
> （`/proc/<pid>/stat`、`thermal_zone*`、`gguf` 落盘），
> **无需 root、无需示波器、无需功耗计**。这正是移动端测量普遍缺失的一环。

### 5e.4 与公开数据的差距（§5 更新）

加压后最坏点 **2.29 t/s**，与官方 1B CPU 47.6 t/s 差 **20.8×**。
但注意：这是**持续满载 12 轮后的劣化点**，非稳态；且模型为 0.5B（搬运更少，本应更快）。
**故 §5 的"混杂未分离"结论不变，此处仅记录劣化幅度。**
→ **该差距已被 §5f 完全解释：绑核差 5.8×（58.72 vs 10.09），与 SoC/模型规模无关。**

## 5f. 绑核对照实验：**机制确认（派活劣化，非后台挤占）**

工具：`tools/core_pinning_test.py`（`os.sched_setaffinity` 绑核，
比外部 `taskset` 更可控）。每组 96 tok，`-r 1`，组间静置 8s。

### 5f.1 结果

| 组 | 绑核 | temp_c | **t/s** | cpu_s | **cpu_ms/tok** | 带宽 GB/s |
|---|---|---|---|---|---|---|
| 1 自由调度 t8 | — | 44.1 | **10.09** | 71.82 | 619.6 | 2.580 |
| 2 自由调度 t8（重复） | — | 42.9 | 10.48 | 65.66 | 612.1 | 2.679 |
| 3 **全大核 t4** | **{4,5,6,7}** | 43.8 | **58.72** | **7.69** | **56.1** | **15.012** |
| 4 全大核 t4（重复） | {4,5,6,7} | 43.5 | 58.46 | 7.69 | 56.2 | 14.946 |
| 5 单大核 t1 | {4} | 43.8 | 15.41 | 7.58 | 63.9 | 3.940 |
| 6 小核组 t4 | {0,1,2,3} | 44.1 | 9.26 | 45.99 | 367.1 | 2.367 |

### 5f.2 结论：绑大核 = 5.8 倍增益

```
自由调度 10.29 t/s  vs  全大核 58.59 t/s   →  +469.7%
重复组 10.09/10.48 vs 58.72/58.46           →  增益可复现，非噪声
```

**同温度（43.5–44.1°C）、同字节（243.81 MiB/token），仅改绑核 → 5.8×。**
§5e 的"机制未定"由此收敛：**walt 把 8 线程派到异构核（含大量小核）并产生迁核开销；
锁死大核即消除。**

**同时推翻"后台挤占"假设**：若为后台占 CPU，绑核不会带来 5.8×。

### 5f.3 对 §5e 等比结论的修正（**重要**）

```
cpu_ms/tok:  619.6 → 56.1   降 11.0×
t/s:          10.29 → 58.59  升 5.70×   （组均值；单点对比 10.09→58.72 为 5.82×）
→ 两比值背离（11.0 vs 5.70），等比关系破坏
```

**§5e 的"等比（纯算力缩放）"仅在"绑核方式不变"的同组内成立，不可外推到跨组比较。**
修正表述：`cpu_ms/tok` 度量**算力供给**（受派活影响，可差 11×）；
t/s 是**吞吐**。跨配置时二者不必等比，因为绑核同时改变了并行效率与调度开销。
§5e 用于判别"算力 vs 内存"（同组内比较）**依然有效**。

### 5f.4 两条旁证（内部一致性）

| 检查 | 实测 | 期望 | 判定 |
|---|---|---|---|
| 单大核/全大核 | **0.26** | 0.25（线性） | ✓ 完美线性，无隐藏并行开销 |
| 小核组/全大核 | **0.16** | 0.72（1804/2496） | ✗ 远低于频率比 |

小核组只有频率比的 0.16 倍 → **小核不仅频率低，每 token 效率亦更差**。
且**小核绑核(9.26) < 自由调度(10.09)** → 自由调度确实把线程派进了小核，
**从反面印证 §5f.2**。

### 5f.5 对本课题的意义

1. **移动端推理的第一优化项不是内核优化、不是量化、不是温控，是绑核。**
   一行 `sched_setaffinity` 换 5.8×，而其余优化项都在讨论这之后。
2. **既有文献测量普遍未固定绑核**（§5 表中官方 47.6 t/s 等），
   故**跨论文比较很可能在比"调度策略"而非"硬件能力"** —— 一个一行代码即可消除的漏洞。
3. 本机最佳 **58.72 t/s（0.5B Q4_0，全大核）** 已**超越**官方 1B CPU 参考 47.6 t/s。
   → **§5 的"4.4× 差距"完全由绑核解释，与 SoC 档次、模型规模均无关。**

## 6. 判读纪律（后续所有采集必须遵守）

1. **起点必须冷机**：关机重启后立刻采集，或静置 ≥15 min。首测热态起点作废。
2. **每点多跑取中位数**（`-r 3`），记录 `tps_spread`；`spread > tps×0.5` 判污染剔除。
3. **温度与 CPU 频率必须同时记录**：
   - 频率降 + 温度升 → 热墙
   - **频率降 + 温度平 → 调度/功耗收缩（本机首测指向此项）**
4. **可用内存必须记录**：内存上涨与 t/s 骤降同现 → 判为后台干扰，不计入曲线。
5. **不写死任何性能数字**：带宽一律由 `bytes_per_token × t/s` 现算，不引用标称带宽。
6. **字节账自洽性校验每次必做**：block 参数 < 总参数、占比落在合理区间。
